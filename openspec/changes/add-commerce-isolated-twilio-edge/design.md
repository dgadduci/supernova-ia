# Design: add commerce isolated Twilio edge

> **Status:** Approved direction. This change implements the first
> commerce-owned T-C adapter bridge in parallel with the existing central
> Twilio webhook and dispatcher. The central surface is preserved
> unchanged.

## Architecture decision

Use a two-process, single-contract design:

```text
Twilio (merchant sender) ── signed webhook ──► T-C adapter ── canonical event ──► NovaOrders core
                                                                                       │
Twilio (merchant sender) ◄── one messages.create ◄── T-C adapter ◄── outbound command ─┘
                                                                                       │
                                                                                  existing
                                                                                  outbox row
                                                                                  in NovaOrders
```

The T-C adapter is **one Railway service per installation** (the same
adapter code, one deployment per commerce). The service may live in the
main Railway ``core`` project — in which case it reaches NovaOrders over
Railway private networking (``*.railway.internal``) — or in any other
Railway project, in which case it reaches NovaOrders over public HTTPS
authenticated by the per-installation shared secret. The URL of every
T-C service is stored on its ``InstalacionTwilioComercio`` row under
``tc_service_url`` so the dispatcher always uses the exact per-commerce
URL.

The two bridge paths share one contract shape:

- **Inbound**: T-C adapter validates the Twilio signature, normalizes the
  native form into a canonical event, signs the event with HMAC-SHA256
  using the installation secret, and POSTs it to NovaOrders'
  internal ingress. NovaOrders decrypts the secret envelope, re-validates
  the HMAC, verifies the installation + commerce + destination authority,
  and delegates to the existing ``ProviderInboundMessageCoordinator``.
- **Outbound**: NovaOrders stages a row in the existing outbox table and
  the central ``OutboundMessageDispatcher.dispatch()`` flow POSTs a
  canonical outbound command to the T-C adapter
  ``/internal/commands/send-message`` endpoint **only when**
  ``COMMERCE_ISOLATED_OUTBOUND_ENABLED=true`` and an active installation
  exists for the row's ``comercio_id``. The adapter authenticates with
  the installation secret (HMAC), performs exactly one ``messages.create``
  through the durable per-installation idempotency claim, and returns
  the SID + status. When the flag is off or no active installation
  exists the dispatcher falls back to the documented central Twilio
  path on the same row.

The empty TwiML ``<Response></Response>`` is returned only after
NovaOrders reports acceptance; any other outcome returns a non-success
HTTP status so Twilio retries. The adapter never embeds a ``<Message>``
in that payload.

## Installation registry

### Data model

``InstalacionTwilioComercio`` is a new SQLAlchemy model:

- ``id``: internal PK.
- ``id_comercio``: FK to ``comercios.id`` (``ON DELETE RESTRICT``),
  indexed.
- ``tc_service_url``: the Railway service URL of the T-C adapter that
  belongs to this installation. ``String(512)``, non-null. The
  dispatcher uses the per-installation URL — never a global base URL —
  so commerces may live in different Railway projects.
- ``instalacion_id``: opaque, fixed-length 24-character random id
  generated by the service. ``String(24)``, unique, indexed. Acts as the
  single selector on the ingress path.
- ``activo``: ``Boolean``, default ``True``.
- ``secreto_envelope``: ``Text``. The Fernet envelope of the per-installation
  shared secret. The plain secret is never stored.
- ``secreto_envelope_kid``: ``String(64)``. Key identifier used to rotate
  the master key without rewriting historical envelopes.
- ``fecha_alta``: timestamp, server-default ``now()``.
- ``fecha_ultima_modificacion``: timestamp, server-default ``now()``,
  ``onupdate=now()``.
- ``fecha_baja``: nullable timestamp.

Constraints:

- Unique index on ``instalacion_id`` (``uq_instalacion_twilio_instalacion_id``).
- Index on ``id_comercio``.
- Partial unique index on ``id_comercio`` ``WHERE activo = true``
  (``uq_instalacion_twilio_one_active_per_comercio``) — the database
  refuses concurrent active duplicates so the bounded provisioning CLI
  cannot race against itself.
- Check ``instalacion_id`` matches ``^[a-z0-9]{24}$`` via the service
  layer (no DB CHECK because the regex would require a custom operator;
  the service validates before insert).

### URL validation

The per-installation ``tc_service_url`` is validated by
:func:`backend.services.instalacion_twilio_comercio_service.validate_tc_service_url`:

* the value must be a non-empty stripped string;
* the scheme must be ``https`` for public URLs;
* plain ``http`` is allowed only for hostnames that match the
  documented Railway private networking pattern (``*.railway.internal``);
* the URL must not carry credentials, query string or fragment;
* the URL must be absolute (``scheme://host[/path]``).

``COMMERCE_ISOLATED_TC_BASE_URL`` is renamed to
``COMMERCE_ISOLATED_TC_BASE_URL_LEGACY`` and is no longer the routing
authority. It is preserved only for backward compatibility with
operators who had configured it; the dispatcher never reads it.

### Idempotency registry

``InstalacionTwilioComercioIdempotencia`` is a small operational table
that serialises concurrent outbound dispatchers through the database
and is the durable state machine for the bounded retry contract:

- ``id``: internal PK.
- ``instalacion_id``: FK to ``instalaciones_twilio_comercio.instalacion_id``
  (``ON DELETE RESTRICT``).
- ``idempotency_key``: ``String(128)``, non-null. Bounded CLI derives
  it as ``outbox-{id}``.
- ``estado``: ``String(16)``. One of ``in_progress``, ``sent``,
  ``retryable``, ``terminal``.
- ``message_sid``, ``codigo``, ``http_status``: typed outcome fields
  populated when the T-C adapter returns a typed response.
- ``fecha_creacion``, ``fecha_ultima_modificacion``: timestamps.

The four documented states map to the following contract:

- ``in_progress`` — the bounded dispatcher has staged the claim and
  has not yet seen a typed response. The state is the durable marker
  for an ambiguous network result (timeout, connection drop, malformed
  body): the helper raises :class:`OutboundCommandAmbiguous` so the
  bounded CLI can finalize the outbox row as ``retryable`` while the
  durable claim remains ``in_progress`` for recovery. Concurrent
  claims on the same key serialise through the unique index; the
  loser returns the durable state without calling T-C. The duplicate-
  send protection is preserved after an ambiguous timeout because the
  row stays in ``in_progress`` and the next dispatch short-circuits
  to the durable state instead of firing a new ``messages.create``.
- ``sent`` — the T-C adapter returned a SID. The claim is permanent
  in this phase; the same key returned to a second caller
  short-circuits with the known SID and never fires a second
  ``messages.create``. The bounded CLI never deletes ``sent`` claims
  in this phase.
- ``retryable`` — the T-C adapter or the bounded CLI drove a bounded
  retryable failure. The next dispatch atomically transitions the
  row back to ``in_progress`` through a single
  ``UPDATE ... WHERE estado = 'retryable'`` statement and performs a
  new HTTP call. Two concurrent callers on the same ``retryable`` row
  serialise through the predicate: only one wins and runs the new
  send; the other returns the durable state without calling T-C. The
  bounded CLI keeps the same ``idempotency_key`` and never deletes
  the row.
- ``terminal`` — the T-C adapter returned a status code in the
  closed terminal ``4xx`` set (``400`` / ``401`` / ``403`` / ``404``
  / ``409`` / ``422``). The claim is permanent in this phase; the
  same key returned to a second caller short-circuits with the
  known terminal failure and never fires a second
  ``messages.create``. Any other ``4xx`` status code is NOT
  ``terminal`` — it is treated as an ambiguous result so the helper
  raises :class:`OutboundCommandAmbiguous` and the durable claim
  stays ``in_progress``. The bounded CLI never deletes ``terminal``
  claims in this phase.

Constraints:

- Unique index on ``(instalacion_id, idempotency_key)``
  (``uq_instalacion_twilio_idempotencia_installation_key``). The
  database-level unique constraint is the serialisation point for the
  ``INSERT`` race: a concurrent dispatcher that loses the ``INSERT``
  short-circuits to the durable state and never reaches
  ``messages.create``.
- Index on ``instalacion_id``.

The table is intentionally small and operational only. It carries no
pedido, no cliente, no canal and no catalog state. The bounded CLI
does not delete rows in this phase: deleting a claim would let the
bounded CLI re-issue a ``messages.create`` for a previously-sent
key, which would break the documented duplicate-send guarantee.
Operations that need to drop historical rows belong to a future
operator-only change that is explicitly out of scope.

### Encryption at rest

``InstalacionSecretEnvelope`` is a small dataclass that wraps the Fernet
``Fernet`` library from the standard ``cryptography`` package:

```text
plain secret = secrets.token_urlsafe(32)
envelope     = Fernet(master_key).encrypt(plain secret)
master_key   = COMMERCE_INSTALLATION_MASTER_KEY from env
              (Fernet URL-safe base64-encoded 32-byte key)
```

The master key is loaded once per process and is never logged. A missing
or invalid ``COMMERCE_INSTALLATION_MASTER_KEY`` when
``COMMERCE_ISOLATED_OUTBOUND_ENABLED=true`` (or when the internal ingress
is enabled) causes the FastAPI process to fail closed at startup — the
``uvicorn`` worker never accepts traffic. The envelope store uses
``cryptography.fernet.Fernet`` with multi-key support to enable rotation:

```text
keys = [Fernet(env_master_key)]   # current
if previous_env_master_key is set: keys.append(Fernet(previous_env_master_key))
```

Rotation is automatic: the envelope is decrypted with the first key that
matches. Re-encryption on read is not in scope for this change; a future
operator CLI can rewrite envelopes.

The plain secret is only ever held in:

- the response of the bounded provisioning seam that returns it exactly
  once on installation creation;
- the bounded internal ingress dependency that decrypts on demand and
  re-derives the HMAC.

Both surfaces are operator-only; no owner panel exposes them.

### Provisioning seam

The change does not add an HTTP provisioning endpoint. The bounded
``backend.cli.instalacion_twilio_provision`` CLI is the only seam that
creates a new installation row, generates the secret, persists the
envelope and prints the opaque selector plus the plain secret exactly
once on stdout. Tests cover the CLI directly through ``subprocess.run``
against ``sys.executable -m backend.cli.instalacion_twilio_provision``.

The CLI fails closed at startup when:

* ``COMMERCE_INSTALLATION_MASTER_KEY`` is missing or not a valid Fernet
  URL-safe base64 key (typed
  ``InvalidInstallationMasterKey``);
* ``--comercio-id`` is not a positive integer;
* ``--tc-service-url`` is missing, malformed or fails the documented
  HTTPS / Railway-private-network contract (typed
  ``InvalidInstallationTcServiceUrl``).

```
    ├── __init__.py

    ├── test_canonical_event.py
    ├── test_webhook_route.py
    ├── test_outbound_route.py
    └── test_security_no_secrets.py
```

The adapter does not import any NovaOrders backend module and does not
import SQLAlchemy. It only depends on ``fastapi``, ``pydantic``, ``httpx``
and the Twilio SDK (``twilio.request_validator``,
``twilio.rest.Client``).

### Configuration

``commerce_adapter/app/config.py`` loads the following environment
variables:

- ``TC_HEALTH_HOST`` / ``TC_HEALTH_PORT`` — local bind for ``/health``.
- ``TC_TWILIO_AUTH_TOKEN`` — the merchant Twilio auth token used for
  signature validation and outbound sends.
- ``TC_TWILIO_ACCOUNT_SID`` — the merchant Twilio account SID.
- ``TC_TWILIO_WEBHOOK_BASE_URL`` — the exact public URL Twilio is
  configured to POST to. Used to compose the canonical signature URL.
- ``TC_NOVAORDERS_INGRESS_URL`` — the exact internal URL of the
  NovaOrders ingress endpoint.
- ``TC_INSTALLATION_ID`` — the opaque selector for this installation.
- ``TC_INSTALLATION_SECRET`` — the shared secret NovaOrders issued for
  this installation. Held in memory only.
- ``TC_COMERCIO_ID`` — the bounded internal ``comercio_id`` this
  installation belongs to.
- ``TC_TWILIO_SENDER_E164`` — the merchant Twilio WhatsApp sender.
- ``TC_HTTP_TIMEOUT_SECONDS`` — bounded timeout for NovaOrders calls.
  Default 5.

A missing or invalid value for any required key raises at import time
and the FastAPI app fails to start.

### Webhook endpoint

```text
POST /webhooks/twilio/whatsapp/inbound
   Content-Type: application/x-www-form-urlencoded
   X-Twilio-Signature: <hex>
```

1. The route reads the entire form via ``await request.form()`` so the
   signature validator sees every parameter Twilio signed.
2. It validates ``X-Twilio-Signature`` using the SDK
   ``RequestValidator(TC_TWILIO_AUTH_TOKEN).validate(url, params,
   signature)`` against the exact ``{TC_TWILIO_WEBHOOK_BASE_URL}{path}?{query}``
   URL. A missing or invalid signature returns ``403`` with an empty body
   and zero downstream calls.
3. It builds the canonical event with the four documented Twilio fields
   (``MessageSid``, ``From``, ``To``, ``Body``) plus the installation
   identity (``instalacion_id``, ``comercio_id``) and bounded metadata
   (``profileName`` truncated to a 32-char hash, ``numMedia`` as int).
4. It signs the JSON payload with HMAC-SHA256(``secreto``,
   canonical_bytes) and sends it to ``TC_NOVAORDERS_INGRESS_URL`` with
   ``X-Installation-Signature: hex`` and ``X-Installation-Id:
   instalacion_id``.
5. If NovaOrders returns ``200`` and ``{"status": "accepted"}`` or
   ``{"status": "duplicate"}`` or ``{"status": "rejected", ...}``, the
   route returns ``200 application/xml`` with the body
   ``<Response></Response>``.
6. Any other NovaOrders response (4xx, 5xx, network error) returns
   ``502 Bad Gateway`` with an empty body so Twilio retries. The route
   never sends TwiML containing ``<Message>``.

The route never calls the classifier, recognizer, handler, response
mapper, or any pipeline primitive. It only forwards the event and
returns the empty TwiML.

### Outbound command endpoint

```text
POST /internal/commands/send-message
   Content-Type: application/json
   X-Installation-Id: instalacion_id
   X-Installation-Signature: <hex>
```

The payload:

```json
{
  "instalacion_id": "abc...",
  "comercio_id": 7,
  "idempotency_key": "outbox-123",
  "destinatario_e164": "+5491155556666",
  "cuerpo": "...",
  "status_callback_url": null,
  "proveedor": "twilio"
}
```

Authentication is enforced in this exact order:

1. ``X-Installation-Id`` header presence and exact match against the
   local ``TC_INSTALLATION_ID``. ``401`` on missing or mismatch.
2. HMAC signature recomputation over the raw body bytes against the
   local installation secret. ``401`` on missing or invalid.
3. JSON body parsing against the canonical outbound schema. ``400`` on
   invalid payload.
4. ``instalacion_id`` exact match between body and local config. ``403``
   on mismatch.
5. ``comercio_id`` exact match between body and local config. ``403``
   on mismatch.

Only after all five checks pass:

6. Call exactly one ``Client.messages.create(to="whatsapp:+...",
   from_="whatsapp:+...", body=..., status_callback=...)`` through the
   ``TwilioMessagesClient`` seam. When the command carries ``None`` for
   ``status_callback_url`` the ``status_callback`` kwarg is omitted so
   no placeholder URL is ever persisted.
7. Return ``{"status": "sent", "message_sid": "SM..."}`` on success.
8. Return ``{"status": "retryable", "code": "..."}`` on 429/5xx.
9. Return ``{"status": "terminal", "code": "..."}`` on a status code
   in the closed terminal ``4xx`` set (``400`` / ``401`` / ``403`` /
   ``404`` / ``409`` / ``422``). Any other ``4xx`` status code is
   NOT ``terminal`` — it is treated as an ambiguous result by the
   NovaOrders helper, which raises
   :class:`OutboundCommandAmbiguous` and leaves the durable claim
   ``in_progress`` for recovery.

The route never logs body, phone, token, signature, or credential. Logs
are limited to ``instalacion_id_tail``, ``comercio_id``, ``outbox_id``,
``idempotency_key_tail`` and the typed status.

### Health endpoint

```text
GET /health  → 200 {"status": "ok"}
```

The endpoint is a plain ping and never touches any external service.

## NovaOrders internal ingress

### Path

```text
POST /internal/commerce-installation/{instalacion_id}/accept-event
```

### Auth

A FastAPI dependency:

1. Read ``X-Installation-Signature`` header.
2. Load the installation row by ``instalacion_id`` (404 on miss).
3. Decrypt the envelope, fail closed if the envelope cannot be decrypted.
4. Recompute HMAC-SHA256(plain secret, body bytes) and reject on mismatch.
5. Verify the installation is ``activo``.
6. Inject the installation, comercio and plain secret into the request
   handler as a typed dependency.

The dependency never returns the plain secret in a response and never
logs it.

### Handler

```text
def accept_event(instalacion_id: str,
                 installation: InstalacionTwilioComercio,
                 body: bytes,
                 signature: str,
                 payload: CanonicalInboundEvent,
                 session: DatabaseSession = Depends(get_session)) -> Response:
```

1. Validate the four required canonical fields are non-empty.
2. Resolve the active ``CanalWhatsapp`` for the installation's
   ``comercio_id`` whose ``destination_e164`` matches ``payload.to_e164``.
   Use the existing ``CanalWhatsappRepository``.
3. Resolve the existing active ``Cliente`` for ``payload.from_e164`` via
   ``ClienteRepository.get_by_whatsapp``. A miss is a typed
   ``unknown_client`` outcome that returns ``{"status": "rejected",
   "reason": "unknown_client"}`` with HTTP ``200`` (the T-C adapter still
   returns the empty TwiML because the event was durably classified as
   a no-op for that commerce).
4. Verify availability with
   ``CommerceAvailabilityService.evaluate(comercio_id)``.
5. Build a ``ProviderInboundMessageCommand(proveedor=proveedor,
   identificador_recepcion=message_sid, canal_id=..., cliente_id=...,
   comercio_id=..., mensaje=body, destinatario_e164=from_e164)``.
6. Invoke the existing ``ProviderInboundMessageCoordinator.accept``.
7. Map the coordinator outcome to the documented JSON response:
   - ``ACCEPTED`` → ``{"status": "accepted", "receipt_id": ...}``
   - ``ALREADY_PROCESSED`` → ``{"status": "duplicate", "receipt_id": ...}``
   - ``INVALID_CONTEXT`` → ``{"status": "rejected", "reason": source}``
8. Persist and stage one ``MensajeProveedorSaliente`` outbox row for the
   response only when the existing coordinator's ``process_lease`` path
   does so; in the first version the response is the only durable effect
   of the ingress. Outbound commands are emitted later by the existing
   bounded CLI when the deferred work item is processed.

### Reuse of the coordinator

The ingress delegates to the existing
``ProviderInboundMessageCoordinator.accept`` exactly the same way the
central Twilio webhook does. The coordinator remains the sole transaction
owner for the receipt + work-item pair and is unchanged. The ingress
dependency only loads the installation row.

## NovaOrders outbound command

The existing outbox is reused. The central
``OutboundMessageDispatcher`` is the single owner of the
``MensajeProveedorSaliente`` lease / finalize lifecycle; this change
adds an opt-in seam that, when ``COMMERCE_ISOLATED_OUTBOUND_ENABLED``
is ``True`` and an active installation exists for the row's
``comercio_id``, delegates the network call to the bounded
``OutboundCommandDispatcher`` helper. When the flag is off or no active
installation exists the dispatcher falls back to the documented central
Twilio path on the same row — the bounded CLI never sees two network
calls for the same row.

The helper performs:

1. Resolve the active installation for the row's ``comercio_id``.
2. Validate the per-installation ``tc_service_url`` against the
   documented HTTPS / Railway-private-network contract.
3. Decrypt the installation envelope to obtain the per-installation
   shared secret.
4. Run the durable claim lifecycle through ``(instalacion_id,
   idempotency_key)``:
   - **Phase 1 (fresh claim)** — the helper tries to ``INSERT`` a
     fresh ``in_progress`` row through the unique constraint. The
     winning caller transitions to phase 2 with the new HTTP call
     owned by the helper.
   - **Phase 2 (retryable transition)** — when the ``INSERT`` loses
     the race and the existing row is in ``retryable`` state, the
     helper performs the atomic transition
     ``retryable -> in_progress`` through a single
     ``UPDATE ... WHERE estado = 'retryable'`` statement. The
     winning caller transitions to phase 2 with the new HTTP call
     owned by the helper; the loser's update affects zero rows and
     falls through to phase 3.
   - **Phase 3 (durable state)** — the helper reads the existing
     row and returns the durable state without calling T-C:
     ``sent`` / ``terminal`` / ``in_progress`` are permanent for
     this phase; no second ``messages.create`` call fires.
   The database is the serialisation point for every phase. The
   helper never carries a transaction across the network call, never
   relies on a process-local dictionary and never deletes the claim
   to retry. The ``idempotency_key`` is preserved across the
   transition.
5. Build the canonical outbound command, sign it with HMAC-SHA256 and
   POST it to the per-installation ``tc_service_url/internal/commands/send-message``
   with ``X-Installation-Signature`` and ``X-Installation-Id``.
6. Translate the typed T-C response into the same outbox state machine
   vocabulary the central dispatcher already uses (``sent`` /
   ``retryable`` / ``terminal``) and finalize the durable idempotency
   row to the matching state.
7. When the network call returns no typed response (timeout, malformed
   body) the helper raises :class:`OutboundCommandAmbiguous` so the
   bounded CLI translates the row to ``retryable`` while the durable
   claim row stays in ``in_progress``. A subsequent retry with the same
   key short-circuits to the durable state without firing a second
   ``messages.create`` so the duplicate-send protection is preserved
   after an ambiguous timeout.

The bounded CLI uses two short transactions per HTTP call: the claim
transaction (INSERT or atomic UPDATE) and the finalize transaction
(typed outcome). The two transactions never carry the outbox row,
never touch the central ``MensajeProveedorSaliente`` lease and never
share state with the central dispatcher's caller-owned transaction. The
bounded CLI / central dispatcher stays the single owner of the outbox
lease, the finalize transaction and the commit / rollback discipline.

The bounded CLI never logs body, phone, token, signature or credential.

| --- | --- | --- | --- |

## Ambiguous-result handling (central dispatcher / helper seam)

The helper raises :class:`OutboundCommandAmbiguous` for any of the
following conditions:

- the helper performed the network call and the call returned no
  typed response (timeout, connection drop, malformed body);
- the helper received ``200`` with a body that fails the closed
  ``CanonicalOutboundResponse`` contract (unknown ``status``, missing
  ``message_sid`` on ``"sent"``, extra fields, malformed JSON);
- the helper received a non-200 status code that the closed HTTP
  classification treats as ambiguous (any ``4xx`` outside the
  documented terminal set).

The central ``OutboundMessageDispatcher.dispatch()`` flow catches the
exception, synthesizes an ``OutboundCommandResult`` whose ``status``
is ``"in_progress"`` and finalizes the central
``MensajeProveedorSaliente`` outbox row as ``retryable`` through its
existing caller-owned finalize transaction. The dispatcher
NEVER falls back to the documented central Twilio path on an
ambiguous result — the bounded CLI / outbox lease stays the single
owner of the row and the next dispatch drives the documented
bounded retry path. The helper leaves the durable
``instalaciones_twilio_comercio_idempotencia`` claim row in
``in_progress`` state so a retry on the same key short-circuits to
the durable state without firing a second ``messages.create``. The
duplicate-send protection is preserved across the ambiguous result.

## Closed HTTP classification

The helper classifies non-200 HTTP responses per the closed policy
documented below. The mapping is the single boundary for the bounded
CLI retry semantics. Unknown ``4xx`` codes are NEVER defaulted to
``retryable``: a silent misconfiguration cannot pollute the durable
claim state.

| Status | Outcome |
| --- | --- |
| ``429`` | ``retryable`` with ``code="http_429_rate_limited"`` |
| ``500``-``599`` | ``retryable`` with ``code="http_<status>_provider"`` |
| ``400`` | ``terminal`` with ``code="http_400_contract"`` |
| ``401`` | ``terminal`` with ``code="http_401"`` |
| ``403`` | ``terminal`` with ``code="http_403"`` |
| ``404`` | ``terminal`` with ``code="http_404"`` |
| ``409`` | ``terminal`` with ``code="http_409"`` |
| ``422`` | ``terminal`` with ``code="http_422"`` |
| any other ``4xx`` | ambiguous — claim stays ``in_progress`` and the helper raises :class:`OutboundCommandAmbiguous` |

The list of terminal ``4xx`` codes is closed and explicitly
documented. Adding a new code requires updating the proposal, the
design and the spec so the contract stays closed.

## Closed ``CanonicalOutboundResponse`` contract

``CanonicalOutboundResponse`` is the canonical typed response sent
back by the T-C adapter. The contract is closed:

- ``status`` is restricted to the documented set
  ``{"sent", "retryable", "terminal"}``. Any other value is rejected
  by the Pydantic ``Literal`` validator;
- ``message_sid`` MUST be a non-empty string whenever
  ``status == "sent"`` and MUST be ``None`` otherwise. The Pydantic
  ``model_validator`` enforces the constraint;
- ``code`` is optional and limited to documented safe codes. ``None``
  is the only ``code`` value accepted alongside ``"sent"``;
- any extra field is rejected by the ``extra="forbid"`` policy.

An invalid response — unknown ``status``, missing ``message_sid``
on ``"sent"``, extra fields, malformed body — is treated as an
ambiguous result. The helper raises
:class:`OutboundCommandAmbiguous` so the bounded CLI finalizes the
central outbox row as ``retryable`` while the durable claim row
stays ``in_progress`` for recovery. The helper NEVER finalizes the
durable claim with an invalid state and NEVER fires a second
``messages.create`` call after an invalid response.

## Testing and release gates

Focused tests cover:

- valid Twilio signature → 200 empty TwiML and one forward call to
  NovaOrders with the documented canonical payload and HMAC;
- tampered or missing signature → 403, no forward call;
- missing required Twilio form field → 200 empty TwiML, no forward call;
- NovaOrders unreachable → 502, no TwiML;
- NovaOrders rejection → 200 empty TwiML (the event was durably
  classified);
- duplicate ``MessageSid`` → 200 empty TwiML after the existing
  coordinator's idempotency path;
- isolation: two commerces with two installations, mixed-forwarding is
  rejected;
- installation inactive → 401 at NovaOrders ingress;
- HMAC mismatch on NovaOrders ingress → 401, no coordinator call;
- outbound command without ``X-Installation-Id`` → 401, zero
  ``messages.create`` calls;
- outbound command with mismatching ``X-Installation-Id`` → 401, zero
  ``messages.create`` calls;
- outbound command without signature → 401, zero ``messages.create``
  calls;
- outbound command with mismatching ``instalacion_id`` → 403, zero
  calls;
- outbound command with mismatching ``comercio_id`` → 403, zero calls;
- exactly one ``messages.create`` call per accepted command;
- the canonical contract has no Twilio field names in the payload sent
  to NovaOrders;
- logs and exception traces never contain body, phone, token, signature
  or credential;
- sandbox and production shapes produce the same canonical payload
  (Twilio fields collapse identically);
- per-installation ``tc_service_url`` is used by the dispatcher (not a
  global URL);
- concurrent provisioners cannot insert two active installations for
  the same ``comercio_id``;
- the same ``(instalacion_id, idempotency_key)`` returns the durable
  result on a second call without firing a second ``messages.create``;
- concurrent dispatchers serialise through the unique database
  constraint;
- a timeout / malformed response after ``messages.create`` raises
  ``OutboundCommandAmbiguous`` and leaves the durable claim row
  ``in_progress`` for recovery;
- the central ``OutboundMessageDispatcher.dispatch()`` falls back to
  the documented central Twilio path when the flag is off or no active
  installation exists;
- ``COMMERCE_INSTALLATION_MASTER_KEY`` missing or invalid with the flag
  on refuses to start the NovaOrders process;
- the durable state machine for ``(instalacion_id, idempotency_key)``:
  - first attempt ``429`` then second attempt ``sent`` — exactly two
    real HTTP calls and the claim finalizes as ``sent``;
  - first attempt ``500`` then second attempt ``sent`` — exactly two
    real HTTP calls and the claim finalizes as ``sent``;
  - multiple ``retryable`` attempts before the final ``sent`` — every
    ``retryable`` claim drives a new HTTP call and the claim
    finalizes as ``sent`` only on the final attempt;
  - two concurrent callers on the same ``retryable`` claim — the
    atomic ``UPDATE ... WHERE estado = 'retryable'`` predicate
    serialises them; only one runs the new HTTP call; the other
    returns the durable state without calling T-C; exactly one
    real HTTP call fires for the second attempt;
  - a ``sent`` claim never fires a second ``messages.create``;
  - a ``terminal`` claim never fires a second ``messages.create``;
  - an ``in_progress`` claim (after a timeout) never fires a second
    ``messages.create``;
  - the retryable → sent retry sequence is driven through the real
    ``OutboundMessageDispatcher`` so the bounded CLI / outbox lease
    / finalize path is exercised end-to-end.

Release requires the implementation to land with all the focused
tests passing on ``supernova_test`` and the focused Ruff/compileall/
openspec validation listed in ``proposal.md``. No production Twilio
account, no Railway project, no merchant onboarding or live webhook is
performed by this change.
