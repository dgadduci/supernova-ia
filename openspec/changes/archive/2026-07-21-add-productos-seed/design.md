## Context

Mirrors the prior seed subphases. Code under `backend/db/seeds/` (script in `seeds/` subfolder per the same convention as the other seed scripts). DB selection via `SUPERNOVA_DATABASE_URL` with default `supernova_test`.

Two design points specific to this change:

- **Catalog file indirection.** The product names and descriptions live in `prod_json.json`, a separate file organized by category. `productos.json` (the actual seed file) is generated by taking the cross product of each comercio's `categorias_productos` rows and the catalog entries for each category. Editing the catalog (e.g., adding a new pizza flavor) is a single edit to `prod_json.json` plus a regeneration of `productos.json` plus a re-run of the seed. The script does not know about `prod_json.json`; it only consumes the already-generated `productos.json`.
- **Category name case mismatch.** `prod_json.json` uses uppercase category names (`PIZZAS`, `EMPANADAS`, `BEBIDAS`, `POSTRES`); the existing `categorias_productos` table stores them in title case (`Pizzas`, `Empanadas`, `Bebidas`, `Postres`) from the prior `seeds-categorias-productos` subphase. The script lower-folds both sides of the category lookup so the JSON keys match the DB rows without needing to mutate either source of truth.

## Decisions

- **D1 — One script, one DB at a time.** Same convention as prior seed subphases.
- **D2 — Idempotent on the composite `(id_categoria_producto, nombre)` pair.** Mirrors the model's unique constraint.
- **D3 — Both parent references resolved at insert time.** `comercio_cuit` against `comercios.cuit`; `(comercio_id, categoria_descripcion)` against `categorias_productos`. The category lookup is case-insensitive (lower-folded) to bridge the uppercase-in-JSON / title-case-in-DB gap.
- **D4 — JSON data file, not embedded constants.** Source of truth lives next to the script. The catalog itself (`prod_json.json`) is a separate, human-editable file consumed at generation time.
- **D5 — Unknown parent reference fails loudly.** A typo in `comercio_cuit` or a missing category raises `ValueError` instead of silently inserting nothing.
- **D6 — Presentation references are not encoded in the JSON.** They are descriptive context; the linkage to `Presentacion` belongs to a future `producto_presentaciones` seed.

## Risks / Trade-offs

- **[Risk] Stale `productos.json` after a `prod_json.json` edit.** → Mitigation: the script consumes `productos.json`, not `prod_json.json`, so a catalog edit does not auto-propagate; the operator regenerates `productos.json` and re-runs the seed explicitly. This is intentional: it makes the seed input reviewable as a file.
- **[Risk] Category case changes in `prod_json.json` or `categorias_productos` later.** → Mitigation: the script's lower-folded lookup is robust to either side moving between cases. A change in the actual category name itself (e.g., renaming "Pizzas" to "Pizzas y Empanadas") still requires regenerating `productos.json`.
- **[Trade-off] No global "seed everything" runner.** A future subphase may add one. Out of scope here.
- **[Trade-off] Presentation metadata is not persisted in this JSON.** A future seed of `producto_presentaciones` will need its own data source (or an extension of this JSON) to know which presentation(s) each product is sold in.
