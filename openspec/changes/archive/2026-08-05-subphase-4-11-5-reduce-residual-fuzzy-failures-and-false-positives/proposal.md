## Why

Subphase 4.11.4 archived at `openspec/changes/archive/2026-08-05-subphase-4-11-4-correct-real-fuzzy-product-recognition-failures/` eliminated the calibration-environment defect: the per-commerce `CommerceCatalog` is loaded fresh from PostgreSQL once per commerce per calibration run, the `commerce_catalog_fingerprint` refusal detects drift, and the runner hands the fuzzy recognizer a faithful full runtime-compatible commerce catalog for every `commerce_dynamic_database` case. The post-fix `mismatch_category_counts` aggregate is `correct: 39, real_fuzzy_recognizer_failure: 3, real_hybrid_recognizer_failure: 5, total: 8` (47 − 39 = 8), the seven dataset / seed / identifier categories all sit at `0`, and `mismatch_category` is honestly classified for every case. The archived Subphase 4.11.4 also pinned the post-fix metrics: fuzzy decision accuracy `0.5319`, hybrid decision accuracy `0.8298`, fuzzy false unknowns `3/41`, hybrid false unknowns `7/41`, and the final eligibility verdict `not_eligible` with reason **`false_positive_tolerance_failed`** — the only remaining gate that fails. The remaining 3 fuzzy failures and 1 false-positive case are now genuine recognizer defects on a faithful full-commerce catalog, not calibration-environment artefacts.

The objective of Subphase 4.11.5 is to correct the smallest set of real fuzzy-recognizer defects responsible for (1) the 3 residual fuzzy recognition failures and (2) the false-positive case driving the `false_positive_tolerance_failed` eligibility gate, without re-introducing the regressions the calibration environment was built to prevent. The false-positive tolerance in the dataset eligibility block is `0.0`, so the change must drive `false_positives.count` to `0` while preserving the 39 currently correct cases and not materially increasing fuzzy false unknowns.
