## Context

Subphase 4.11.4 archived at `openspec/changes/archive/2026-08-05-subphase-4-11-4-correct-real-fuzzy-product-recognition-failures/` eliminated the empty-catalog defect in the offline calibration runner. The runner now loads the full runtime-compatible commerce catalog from PostgreSQL once per `id_comercio` per calibration run (`backend/services/product_recognition_calibration_commerce_catalog.py:load_commerce_catalog_from_database`), caches it on `self._commerce_catalog_cache`, refuses to start on fingerprint drift (`StaleCommerceCatalogError`), and hands the fresh DB catalog to the fuzzy recognizer for every `commerce_dynamic_database` case. The post-fix diagnostic evidence committed at `openspec/changes/archive/2026-08-05-subphase-4-11-4-correct-real-fuzzy-product-recognition-failures/diagnostics/after.json` records 47 evaluated cases with `mismatch_category_counts = {correct: 39, real_fuzzy_recognizer_failure: 3, real_hybrid_recognizer_failure: 5, total: 8}` and final eligibility verdict `not_eligible` with reason **`false_positive_tolerance_failed`** — the only remaining failing gate. The runner's `correct_cases, real_fuzzy_recognizer_failure, real_hybrid_recognizer_failure, false_positives, false_unknowns, latency_p95, eligible` are the substrate for any future Subphase 4.12 activation.

The 8 residual failures after Subphase 4.11.4 are catalogued under `real_fuzzy_recognizer_failure` (3) and `real_hybrid_recognizer_failure` (5):

- **3 residual `real_fuzzy_recognizer_failure` cases** — the fuzzy recognizer returns `unknown` for inputs it should resolve:
  - `c1-ambiguous-postre` — input `"un postre"`, `expected_decision: ambiguous`, `allowed_candidate_ids: [69, 70, 71, 72]`. The catalog at `comercio_id=1` has 4 entries under `categoria_nombre: "Postres"` (`Flan casero`, `Tiramisú`, `Helado`, `Brownie con helado`); none of them contain `postre` in `producto_nombre`. The fuzzy `_extraer_candidatos` (`backend/recognizers/product_recognizer.py:402-498`) and `_filtrar_por_tokens_clave` (`:340-364`) match the input against `producto_nombre` only; with no product name containing the token `postre`, the candidate set is empty and the recognizer returns `no_encontrados`. The expected behaviour is that the user implicitly addressed the `Postres` category and the recognizer returns a category-level `encontrados_posibles` group with `kind: "category"`, `categoria_nombre: "Postres"`, and `texto_origen: "un postre"` (the 4 entries are NOT exposed as evaluable product candidates).
  - `c1-fuzzy-vector-disagreement-muzarrella` — input `"muzarrella"`, `expected_decision: unique`, `allowed_candidate_ids: [1, 2]`. The catalog has `pid=1` (`Pizza de Muzzarella GRANDE`) and `pid=2` (`Pizza de Muzzarella CHICA`); both products are reachable through the existing alias map (`muza`, `muzza`, `muzarela`, `mozarela`, `mozarella`, `muzzarela`, `muzzarella`, `musarela`, `musarella`), but the variant `muzarrella` is missing. The fuzzy token `"muzarrella"` is normalized via `_normalizar_palabras_pedido` to the same singular form, and `_aplicar_aliases` (`backend/recognizers/product_recognizer.py:166-168`) consults `ALIASES_PALABRAS` — which is missing the `muzarrella` entry — so the token passes through unchanged and the RapidFuzz `WRatio` against `nombre_normalizado` falls below the `score_minimo` threshold and the candidate set is empty. The expected behaviour is that the alias map closes the typo gap and the recognizer returns the entry as `encontrados`.
  - `c1-ambiguous-pizza-again` — input `"otra pizza"`, `expected_decision: ambiguous`, `allowed_candidate_ids: [1, 2, 3, 4]`. The catalog has 30 entries under `categoria_nombre: "Pizzas"` (every `Pizza de Muzzarella`, `Pizza Napolitana`, `Pizza Margherita`, `Pizza Fugazzeta`, `Pizza Fugazza`, `Pizza Calabresa`, `Pizza de Jamón y Morrones`, `Pizza de Cuatro Quesos`, `Pizza de Provolone`, `Pizza de Roquefort`, `Pizza de Anchoas`, `Pizza Hawaiana`, `Pizza Caprese`, `Pizza Diavola`, `Pizza Especial de la Casa` — each with `GRANDE` and `CHICA` presentations). The token `otra` is not a stopword or `TAMANIOS` entry; `pizza` is a generic category token. The fuzzy pipeline matches `pizza` against `nombre_normalizado` (the entries are `pizza de muzzarella`, `pizza napolitana`, etc.); `fuzz.WRatio` against the longer names produces scores below `score_minimo` for the standalone token `pizza`, and `_filtrar_por_tokens_clave` requires every significant user token to be present in the candidate's `producto_nombre` — neither `otra` nor `pizza` is present in any pizza name. The candidate set is empty and the recognizer returns `no_encontrados`. The expected behaviour is that the user implicitly addressed the `Pizzas` category and the recognizer returns a category-level `encontrados_posibles` group with `kind: "category"`, `categoria_nombre: "Pizzas"`, and `texto_origen: "otra pizza"` (the 30 entries are NOT exposed as evaluable product candidates — exposing them would trigger `candidate_boundary_violation` because the runner's `_flag_fuzzy_boundary_violation` checks every product id against `allowed_candidate_ids: [1, 2, 3, 4]` and 26 of the 30 pizza ids would fail the check).

- **5 residual `real_hybrid_recognizer_failure` cases** — the fuzzy returns the right answer; the hybrid combination overwrites it:
  - `ambiguous-empanada-carne` — input `"empanada de carne"`, `catalog_scope: pending_product_selection_restricted`, `expected_decision: ambiguous`, `allowed_candidate_ids: [11, 12]`. The in-memory catalog `empanada_carne_restricted` has two entries: `pid=11` (`Empanada de Carne PICANTE`) and `pid=12` (`Empanada de Carne TRADICIONAL`). The fuzzy returns ambiguous (11, 12) — the user did not specify a presentation. The vector search returns `unique(11)` — the vector picked the PICANTE presentation. The hybrid `_hybrid_prediction` (`backend/services/product_recognition_calibration_runner.py:170-196`) combines the fuzzy scores `(1.0, 0.5)` and the vector score `(1.0,)` with the policy weights (e.g. `fuzzy_weight=0.5, vector_weight=0.5`) and the combined scores become `(11: 1.0, 12: 0.25)`. The gap (`0.75`) exceeds `policy.minimum_score_gap` and the top score (`1.0`) exceeds `policy.unique_threshold`, so `_decision` (`backend/services/product_recognition_calibration_runner.py:125-144`) returns `unique` — a false positive, because the user did not specify which presentation. This is the single case causing `false_positive_tolerance_failed` (`false_positive_tolerance: 0.0`).
  - `product-plus-presentation`, `fuzzy-misspelling-mozzarella`, `supported-mozza-alias`, `multi-word-jamon-queso-dynamic` — four hybrid cases where the fuzzy returns `unique(pid)` and the vector returns `unknown`, and the hybrid downgrades the fuzzy's `unique` to `unknown`. These are outside this proposal's scope (the brief explicitly excludes fixing the 4 other hybrid-specific failures; only the false-positive case must be addressed).

The recognition pipeline at `backend/recognizers/product_recognizer.py` exposes the standard stopword / size / digit / quantity-word / canonical / alias / score-gap / threshold surface. The 3 fuzzy failures are concentrated in two narrow gaps:
1. A static alias gap (one missing entry in `ALIASES_PALABRAS`).
2. No category-scope matching (the recognizer matches `producto_nombre` only; category-only inputs reduce to `no_encontrados`).

The hybrid false-positive case is concentrated in a narrow gap: when the catalog scope is `pending_product_selection_restricted` and the fuzzy decision is explicitly `ambiguous`, the hybrid policy does not currently preserve the fuzzy's ambiguous signal — the vector's top-1 widens the gap and the hybrid promotes to `unique`. The fix is a positional guard in `_decision` that, when the scope is `pending_product_selection_restricted` AND the fuzzy decision is explicitly `ambiguous` (the equivalent direct evidence being `len(fuzzy_ids) > 1` on `CaseObservation.fuzzy_ids`, OR a category-level `encontrados_posibles` group with `kind: "category"` detected by `_fuzzy_decision(result)`), returns `ambiguous` regardless of the vector's contribution. The guard MUST inspect the fuzzy decision explicitly and MUST NOT infer fuzzy ambiguity from the combined hybrid `ranking` — the combined hybrid ranking is the union of `observation.fuzzy_ids` and `observation.vector_ids`, so a fuzzy-`unique` + vector-`unique(other)` case produces a multi-candidate hybrid ranking even though the fuzzy was not ambiguous.

## Decisions

**Decision 1 — The fix is a 1-line alias entry + a category-scope matching pass + a single hybrid guard + a typed discriminated union for `encontrados_posibles` + reader adaptations, scoped to the 3 fuzzy failures and 1 false-positive case.**

Rationale: the 80/20 strategy in the brief mandates the smallest correction that fixes multiple cases. Priority 1 (local alias correction) covers `c1-fuzzy-vector-disagreement-muzarrella` with a single dictionary entry. Priority 2 (key-token / presentation-filter correction) covers `c1-ambiguous-postre` and `c1-ambiguous-pizza-again` with a single category-scope matching pass. Priority 4 (narrowly-scoped scoring / score-gap correction) covers the false-positive case with a single positional guard on the existing scoring decision. Priorities 3 (segmentation) and 5 (threshold) are not needed. The fix touches 2 production source files (`backend/recognizers/product_recognizer.py`, `backend/services/product_recognition_calibration_runner.py`), 1 typed-contract file (`backend/recognizers/product_recognizer_contract.py`), and adapts 9 production readers across `backend/intents/{resolvers,context,orchestration,recognizers}/` and `backend/services/product_recognition_shadow_service.py`. It adds 1 test file (`backend/tests/test_product_recognition_calibration_4_11_5.py`). Alternatives considered: (a) rebuild the fuzzy recognizer with a learned ranker — rejected because the brief explicitly excludes it; (b) lower the `score_minimo` threshold — rejected because it would inflate false positives and damage the 39 correct cases; (c) raise the `unique_threshold` in the selected policy — rejected because the brief explicitly excludes relaxing the calibrator by changing the policy grid; (d) add the hybrid guard at the case-aggregation layer instead of `_decision` — rejected because the case-aggregation layer would still need to consult the same scope and candidate data and would duplicate the rule; (e) reuse the existing `PossibleMatchGroup` shape for the category-level signal — rejected because it would either expose fake product ids or carry a misleading empty `productos` list (see Decision 9); (f) skip the typed-union formalization and rely on the existing `group.get("productos", []) or []` defaults — rejected because the `product_intent_resolver.py` flat-candidate fallback at line 27 does an unchecked `candidate["producto_presentacion_id"]` and would `KeyError` on a category group; (g) reuse the existing flat-candidate branch by checking `"productos" in group` — rejected because it is implicit and inconsistent with the existing `PossibleMatchGroup` shape.

**Decision 2 — The category-scope matching pass runs after `_extraer_candidatos` and `_filtrar_por_tokens_clave`, signals category-level ambiguity through the typed-discriminated-union `encontrados_posibles` flow, and never exposes every entry in the matched category as an ordinary product candidate.**

Rationale: the existing fuzzy pipeline already filters out candidates whose `producto_nombre` does not contain every significant user token (the `_filtrar_por_tokens_clave` discipline). The 3 fuzzy failures occur because the user's input reduces to a category-only token (e.g., `postre`, `pizza`) that no product name contains. The category pass runs only when the existing pipeline produced no product candidates for the segment AND a significant user token matches a catalog `categoria_nombre`; it appends a category-level `encontrados_posibles` group carrying the explicit discriminator `kind: "category"`, `texto_origen` (the original segment), and `categoria_nombre` (the normalized category name) — the group does NOT carry a `productos` list and the matched catalog entries are NOT exposed as evaluable product candidates. The pass never removes an existing product candidate, never bypasses `_filtrar_por_tokens_clave`, never bypasses `_extraer_presentacion`, never bypasses the availability flags, never bypasses the `STOPWORDS` / `TAMANIOS` / `PALABRAS_CANTIDAD` discipline, and never changes the four top-level result keys (`encontrados`, `encontrados_posibles`, `encontrados_no_disponibles`, `no_encontrados`). The existing product-level `encontrados_posibles` group shape (`{"texto_origen": ..., "productos": [...]}`) is preserved byte-identically (no `kind` field is added to the product-level variant); the new category-level group is a NEW variant in the typed union. The pass is deterministic and runs in a single linear scan over the catalog's categories per input segment. The runner's `_fuzzy_decision` helper inspects the result and returns `"ambiguous"` whenever a category-level group is present, otherwise it falls back to the existing id-based logic (`"unique"` if `len(fuzzy_ids) == 1`, `"ambiguous"` if `len(fuzzy_ids) > 1`, `"unknown"` if `len(fuzzy_ids) == 0`); the runner's `_decision` returns `"ambiguous"` when the combined ranking is empty AND the fuzzy decision is `"ambiguous"` (category-level), and returns `"unknown"` otherwise. The runner's `_flag_fuzzy_boundary_violation` does NOT fire for category-level inputs because no product ids are extracted from the category-level group. Alternatives considered: (a) reuse the existing `PossibleMatchGroup` shape for the category-level signal (carry a `productos: []` field and add a `kind: "category"` discriminator) — rejected because the field name `productos` is misleading for a category-level group (no products are listed); (b) extend the `no_encontrados` list with a `kind: "category"` field — rejected because `no_encontrados` is documented to carry unmatched message fragments only, and the category-level signal must coexist with the existing product-level `encontrados_posibles` groups (a category pass on a multi-segment input that produced a product-level group on a separate segment must still carry the category group); (c) replace `PossibleMatchGroup` with a single flexible shape — rejected because the byte-identical preservation of the existing product-level variant is a hard constraint.

**Decision 3 — The category-scope matching is gated by the existing `tokens_significativos` filter and respects `STOPWORDS`, `TAMANIOS`, `PALABRAS_CANTIDAD`, and pure-digit tokens.**

Rationale: the existing `tokens_significativos` helper (`backend/recognizers/product_recognizer.py:343-350`) is the single source of truth for "what tokens count toward matching"; reusing it guarantees the category pass never reads stopwords, size terms, or quantity words as categories. The `PALABRAS_CANTIDAD` map (`un`, `uno`, `dos`, `tres`, ...) is excluded so that `un postre` does not treat `un` as a category token. The pass only consumes tokens that survived the filter — i.e. tokens that the existing pipeline would have tried to match against `producto_nombre` if a candidate existed. This preserves the existing token discipline and prevents the category pass from introducing new false positives. Alternative considered: (a) re-implement the token filter inside the category pass — rejected because it duplicates the contract and risks drift.

**Decision 4 — The category-scope matching normalizes the catalog's `categoria_nombre` once per call via the existing `_normalizar_palabras_pedido` and `_singularizar_simple` helpers, and returns the normalized category NAME (a single string) rather than the matching catalog entries.**

Rationale: the catalog's `categoria_nombre` values are plural forms (`"Pizzas"`, `"Postres"`, `"Empanadas"`, `"Bebidas"`) and the input is normalized to singular form via `_singularizar_simple`. To match `pizza` against `Pizzas`, the catalog value must be lowercased and singularized to `pizza`. The existing helpers handle the symmetry: `_normalizar_palabras_pedido` lowercases and removes diacritics, `_singularizar_simple` strips the trailing `s` (or `es` for words longer than 5 characters). The normalization is performed once per call and the result is cached in a `dict[str, str]` keyed by the original `categoria_nombre` (lowercased). The cache is local to the call and discarded when `detectar_productos` returns; it is not a module-level cache. The cache is deterministic (no clock, no randomness, no environment variable). The helper returns the normalized category NAME (a single string, e.g. `"pizzas"` / `"postres"`); it does NOT return the list of catalog entries in that category, and it does NOT consult `allowed_candidate_ids`, `restricted_candidate_ids`, `expected_producto_presentacion_id`, or any calibration label. **Decision 9 — `encontrados_posibles` is formalized as a typed discriminated union in `backend/recognizers/product_recognizer_contract.py` containing two variants: `PossibleMatchGroup` (existing, byte-identical) and `CategoryAmbiguityGroup` (new).**

## Risks / Trade-offs

- [Risk] The category-scope matching pass could introduce false positives — a customer input that happens to match a category token could trigger unrelated catalog entries. → Mitigation: the pass is gated by (1) the existing `tokens_significativos` filter (no stopword, size term, quantity word, digit, or token shorter than 3 characters is treated as a category), (2) the requirement that the existing fuzzy pipeline produced no product candidate for the segment (the pass is a fallback, not a parallel pass), and (3) the category-level signal is exposed through the typed-union `encontrados_posibles` flow with `kind: "category"` and `categoria_nombre` rather than expanding the matched entries into ordinary product candidates — the caller still has to confirm the choice, and the boundary check at `_flag_fuzzy_boundary_violation` does NOT fire because no product ids are extracted from the category-level group. Regression tests assert the 39 correct cases do not regress; a no-regression test specifically pins that an input whose existing pipeline produced a product candidate (e.g., `"pizza muzza"`) does not receive spurious category-level groups, and a separate no-regression test pins that the existing product-level `encontrados_posibles` shape is preserved byte-identically for product-level inputs.

- [Risk] The typed-discriminated-union widening could be misread as a wholesale schema change. → Mitigation: the four top-level result keys (`encontrados`, `encontrados_posibles`, `encontrados_no_disponibles`, `no_encontrados`) are preserved unchanged; the existing product-level `PossibleMatchGroup` shape (`{"texto_origen": ..., "productos": [...]}`) is preserved byte-identically (no `kind` field is added); the only new shape is the `CategoryAmbiguityGroup` (`{"kind": "category", "categoria_nombre": ..., "texto_origen": ...}`); the widening is a strictly backward-compatible addition to the `encontrados_posibles` element type (`list[PossibleMatchGroup | CategoryAmbiguityGroup]`). The proposal documents the widening honestly: "the public `ProductRecognizerResult` typed contract is preserved (the four keys are unchanged; the existing product-level group shape is unchanged); the `encontrados_posibles` element type is widened through a backward-compatible typed discriminated union".

- [Risk] A production reader that accesses `encontrados_posibles` could be missed by the reader-adaptation pass. → Mitigation: the Context section enumerates EVERY production reader of `encontrados_posibles` (the calibration runner, the shadow service, the `agregar_producto` resolver, the `quitar_producto` recognizer and orchestrator, the `modificar_producto` recognizer and resolver, the product-selection context resolver, the order-line selection resolver, and the product modification resolver).
