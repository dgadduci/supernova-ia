## Why

The interactive CLI chat client (`backend.scripts.cli_chat_client`) is the only tool that drives the modern pipeline end-to-end, but it currently shows only the customer-facing response and the draft `Pedido` table. Recent subphases (3.32.3, 3.32.4, 3.32.5) touched the exact inputs and outputs of the classifier and the product resolver, and there is no way for the developer to see those inputs and outputs in real time. Without per-call classifier/resolver traces, queue promotion bugs, stale serialized state, and misrouted candidates are diagnosed by reasoning about the wire response, not by reading the actual data flow. This subphase adds an opt-in `--debug-flow` diagnostic mode that prints classifier input + output and resolver input + output tables for every real call, so the operator can verify the data flow from the CLI without touching the server.

## What Changes

- Add an opt-in `--debug-flow` CLI flag to `backend/scripts/cli_chat_client.py` that activates diagnostic tables without changing default behavior.
- Add an optional `--debug-components classifier,resolver,pending` filter that scopes which components emit tables; default under `--debug-flow` is all three.
- Extend the FastAPI incoming-messages router with a debug-only `X-Debug-Flow` request header that, when present, instructs the orchestrator to attach a `diagnostics` array to the response payload, capturing every classifier call (input and output) and every resolver call (input, candidate catalog, output, matches) invoked during that one incoming message.
- Add a backend diagnostics module with structured event types (`ClassifierCallStarted`, `ClassifierCallCompleted`, `ResolverCallStarted`, `ResolverCallCompleted`, `PendingStateSnapshot`), a `DiagnosticSink` protocol, and a `NoopDiagnosticSink` default. The default sink adds no behavior, no logging, and no allocations in the hot path.
- Instrument the real classifier call (the single `IntentClassifier.query` invocation in the incoming-message orchestrator) and every real resolver call reachable from the incoming-message pipeline (initial product resolution, `ProductSelectionContextResolver`, pending-context resolver, candidate refinement after promotion, and the `modificar_producto` resolver when it shares the path).
- Capture the exact objects passed to and returned from the real call (no duplicate invocations, no reclassification, no ghost resolver calls). The sink is invoked immediately after the real call returns, capturing the real input and the real output.
- Add a safe recursive serializer (`backend/diagnostics/serializer.py`) for dataclasses, Pydantic models, enums, SQLAlchemy projection rows already detached or already loaded, dicts, lists, tuples, and primitives. It must redact secret-named fields (`password`, `token`, `api_key`, `authorization`, `secret`, `database_url`) as `<redacted>`, avoid lazy-loading arbitrary ORM relationships, avoid recursion loops, avoid object memory addresses, and produce deterministic output (sorted keys, stable ordering, `ensure_ascii=False`).
- Add a CLI diagnostic rendering module (`backend/scripts/cli_chat_client_debug.py` or in-module helpers) that consumes the `diagnostics` array from the response and prints `CLASSIFIER INPUT`, `CLASSIFIER OUTPUT`, `RESOLVER INPUT`, `RESOLVER CANDIDATES`, `RESOLVER OUTPUT`, `RESOLVER MATCHES`, `PENDING STATE`, and `PENDING QUEUE` tables with sequential `CLS-NNN` / `RES-NNN` call IDs and a `TURN N` header, using the same stdlib-only table formatter style as the existing `format_order_table`.
- Add a redaction helper (`_redact_payload`) used by both the backend serializer and the CLI renderer, so secrets never reach the terminal.
- Add focused unit tests for the serializer (dataclasses, Pydantic, enums, redis, recursion, secret fields), the diagnostic event payload shape, the `X-Debug-Flow` header activation, the CLI flag parsing, the disabled-by-default contract, the no-duplicate-call contract, and the existing business regressions for `agregar_producto`, `quitar_producto`, `modificar_producto`, the pending queue, and the incoming-message HTTP flow.

## Capabilities

### New Capabilities

- `cli-classifier-resolver-flow-debug`: Opt-in CLI diagnostic mode for the interactive chat client that prints structured classifier and resolver data-flow tables for every real call during a conversation. Disabled by default; activated only by `--debug-flow`.

### Modified Capabilities

- `incoming-messages-interactive-cli`: The CLI accepts a new `--debug-flow` flag and an optional `--debug-components` filter. When `--debug-flow` is enabled, the CLI sends an `X-Debug-Flow` header on every `POST /comercios/{comercio_id}/clientes/{cliente_id}/incoming-messages` request, parses the `diagnostics` array from the response, and renders the tables. When disabled, the CLI behavior and output remain unchanged.
- `intent-classifier`: The incoming-message orchestrator calls a `DiagnosticSink` immediately before and after the real `IntentClassifier.query` call. The default sink is a no-op; the active sink (CLI debug sink) receives `ClassifierCallStarted` and `ClassifierCallCompleted` events with the exact input message, the active context, the resolved prompt metadata, the validated result, and the call ID.
- `context-type-resolver`: The product-selection pipeline emits `ResolverCallStarted` and `ResolverCallCompleted` events for every real resolver invocation, including the initial product resolution, the `ProductSelectionContextResolver` candidate refinement, the pending-context resolver, and the resolver invoked after a queued intent is promoted. The default sink is a no-op.
- `product-selection-context-resolver`: The resolver emits diagnostics only when a non-noop sink is active. The events include the resolver input (intent, source text, quantity, status, requirements, candidate IDs, candidate catalog), the resolver output (status, selected candidate, requirements, resolved data, remaining candidate IDs, rejection reason, clarification message), and the pending-state snapshot. No business behavior changes.
- `incoming-message-orchestrator`: The orchestrator builds the final response payload. When the request carries the `X-Debug-Flow` header, the response payload includes a `diagnostics: list[dict]` field (sorted by call ID, then sequence) that aggregates every event emitted during that one incoming message. The default response (no header) keeps the exact same shape as before.

## Impact

- Modified files: `backend/scripts/cli_chat_client.py` (new `--debug-flow` and `--debug-components` flags, debug-mode branch in the receive loop, debug rendering helpers, redaction helper), `backend/routers/incoming_messages.py` (attach the `X-Debug-Flow` header to a request-scoped `DiagnosticSink`, return the `diagnostics` array when the header is present), `backend/services/incoming_message_service.py` or the equivalent orchestrator module (inject the sink, call the sink before and after the real classifier/resolver calls), `backend/llm/intent_classifier.py` (emit `ClassifierCallStarted` / `ClassifierCallCompleted` through the injected sink; the sink is a no-op by default), `backend/intents/context/context_type_resolver.py` and any sibling resolver modules (emit `ResolverCallStarted` / `ResolverCallCompleted` through the sink), `backend/intents/context/product_selection_context_resolver.py` (emit the resolver input + output events), and `backend/tests/test_cli_chat_client.py` (new tests for the diagnostic mode).
- New files: `backend/diagnostics/__init__.py`, `backend/diagnostics/events.py` (event dataclasses / Pydantic models), `backend/diagnostics/sink.py` (`DiagnosticSink` protocol + `NoopDiagnosticSink` + `CollectingDiagnosticSink`), `backend/diagnostics/serializer.py` (safe recursive serializer with redaction), and `backend/tests/test_diagnostics.py` (focused serializer + sink + event shape tests).
- Reused unchanged: the existing `urllib.request` import boundary in the CLI, the existing `incoming-messages` JSON endpoint contract (no schema change in the default case), the existing customer-facing response logic, the `IntentClassificationResult` schema, the `ProcessedIntent` schema, the `PendingIntents` FIFO queue, the `PedidoDetalleResponse` endpoint, the `ORDER_MUTATING_INTENTS` constant, the existing `format_order_table` helper, the `--base-url` flag, the `INCOMING_MESSAGES_BASE_URL` env var, the close-on-exit contract, the empty-input / `exit` handling, the test `FakeResponse` helper, the test mock patterns for `urllib.request.urlopen` and `builtins.input`.
- Not touched: any existing capability that is not listed in "Modified Capabilities" (no new production endpoint, no schema change for the default response, no classifier prompt change, no resolver threshold change, no intent ordering change, no transaction ownership change, no Twilio adapter, no WebSocket adapter, no queue worker, no LLM call from the CLI, no background polling, no persistent diagnostic storage, no new third-party dependency, no new logging framework, no new table library, no new client framework).
- Not introduced: any diagnostic field in the default response (no `X-Debug-Flow` header → no `diagnostics` field), any secret exposure (the serializer redacts `password`, `token`, `api_key`, `authorization`, `secret`, `database_url` as `<redacted>`), any duplicate classifier/resolver call (the sink observes the real call and never re-runs it), any commit or rollback for diagnostics, any cross-process state, any new model, any Alembic migration, any database column, any HTTP / FastAPI / SQLAlchemy / repository / service import in the CLI module.
