## Why

Subphase 3.30 shipped the standalone CLI HTTP client for exercising the modern intents pipeline. Real manual conversations against `POST /incoming-messages` surfaced three defects that prevent the CLI from being a useful iteration tool: a CLI-created session is born without the draft `Pedido` the `agregar_producto` handler requires, so any positive resolution against the CLI is rejected; a definitive `rejected` handler result leaves the pending context pinned, so the next unrelated message is rerouted into the same dead intent; and the product-selection resolver only recognises a unique match, so a partial narrowing reply (e.g. "la grande" against five candidates) does not refine the candidate set and the conversation stalls. Subphase 3.30.1 fixes these three defects without introducing new CLI features, new endpoints, or new layers.

## What Changes

- **CLI client creates the draft `Pedido` through the existing HTTP API.** After `POST /sessions` returns a session id, the CLI calls `POST /pedidos` with `{"id_session": <session_id>}` and stores the returned `pedido_id`. The CLI does NOT import SQLAlchemy, repositories, or services; everything happens through `urllib.request` against the running API. The session created by the CLI is then enriched through the existing `PUT /sessions/{session_id}/pedido` association so the running pipeline sees `session.id_pedido` set. If the pedido creation fails, the CLI closes the session it created and exits non-zero. The CLI still closes only the session it created on exit.
- **The `pending-context-execution` boundary clears context on a definitive `rejected` handler result.** When `execute_agregar_producto` returns `status == "rejected"` (or any other currently-supported handler returns `rejected`), the function now calls `clear_pending_context(session)` exactly once and sets `session.context_type = None` before returning the rejected intent. The `executed` branch is unchanged. The `failed` branch remains a non-definitive outcome and preserves context (current behavior). A raised technical exception inside the handler still propagates unchanged so the wrapper's `db.rollback()` is preserved.
- **The product-selection resolver refines `candidate_ids` on partial answers.** When the dispatcher calls `resolve_product_selection(message, active_intent, productos_presentaciones)` with a `pending_resolution` intent whose `candidate_ids` is non-empty and the recognizer returns multiple items in `encontrados_posibles`, the resolver returns a new `ProcessedIntent` whose `candidate_ids` is the intersection of the original `candidate_ids` with the matched `producto_presentacion_id`s. The narrowed intent keeps `status == "pending_resolution"` (for >1 candidates) or transitions to `ready` (for exactly 1 remaining candidate that also satisfies the recognition contract), so the dispatcher can route straight to `execute_ready_pending_context` when the refinement happens to leave exactly one option. The unique selection contract is unchanged for exact matches. If the refinement leaves zero candidates, the resolver returns the input unchanged (no infinite narrowing loops).
- **Regression coverage for the five-message `agregar_producto` conversation.** `backend/tests/test_cli_conversation_regression.py` exercises the real CLI loop over HTTP against `supernova_test` with a seeded catalog of five presentations (three `pizza ... grande`, two `pizza ... chica`) and asserts: `quiero dos pizzas` → five candidates, `la grande` → three large candidates only, `Pizza de Muzzarella Grande` → `executed` with one `PedidoProducto` row carrying `cantidad == 2` and the seeded `precio_unitario`. The suite also asserts: an exact unique candidate executes in the same turn without a confirmation prompt; a definitive `rejected` result clears `session.context_type` and `session.pending_intents`; the next unrelated message re-enters initial classification; a raised technical exception propagates and the wrapper rolls back; and the CLI cleanup still issues `POST /sessions/{session_id}/cerrar` exactly once.

## Capabilities

### New Capabilities

_None._ The fixes are bug fixes against existing capabilities.

### Modified Capabilities

- `incoming-messages-interactive-cli`: The CLI bootstrap now creates a draft `pedido` through `POST /pedidos` and associates it with the new session through `PUT /sessions/{session_id}/pedido` before the read-eval-print loop, so the modern handler layer finds `session.id_pedido` set. The CLI still owns one session per run and still closes only the session it created.
- `pending-context-execution`: `execute_ready_pending_context` now clears `session.pending_intents` and `session.context_type` when the dispatched handler returns `status == "rejected"`, in addition to the existing `executed` branch. The `failed` branch remains unchanged and continues to preserve context. Raised technical exceptions inside the handler continue to propagate unchanged so the transaction wrapper's `db.rollback()` is preserved.
- `product-selection-context-resolver`: `resolve_product_selection` now narrows the active intent's `candidate_ids` when the recognizer returns multiple items in `encontrados_posibles` whose `producto_presentacion_id`s are all still within the original `candidate_ids`. The narrowed intent keeps `status == "pending_resolution"` for >1 candidates and transitions to `ready` for exactly 1 candidate (the unique-selection contract is reused). An empty intersection returns the input unchanged. The existing input-validation, no-side-effect, and unique-selection requirements are unchanged.
