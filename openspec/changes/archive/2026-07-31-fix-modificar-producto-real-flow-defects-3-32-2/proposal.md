## Why

Subphase 3.32.1 (`fix-modificar-producto-atomicity-quantity-3-32-1`) declared the two real-flow defects corrected:

1. **Defect 1 — Omitted quantity must transfer the full source-line quantity.** Initial Pedido: `Empanada de Verdura x4`. User sends `cambia las empanadas de verdura por empanadas carne picante`. Expected: source removed, destination created with `cantidad == 4` (never `1`).
2. **Defect 2 — Invalid or unknown destination must preserve the source atomically.** Initial Pedido: `Empanada de Jamón y Queso x5`. User sends `cambia las 5 empanadas de jamon y queso por un caramelo` (`caramelo` is not in the comercio catalog). Expected: one `rejected` `modificar_producto` outcome, source remains `cantidad == 5`, no destination line, Pedido unchanged, no separate `quitar_producto`/`agregar_producto` executions, no partial mutation.

Real CLI testing against the running local FastAPI app still reproduces both defects: the destination receives `cantidad == 1` instead of `4` and the source line is removed before destination validation rejects `caramelo`, leaving the Pedido with `Empanada de Jamón y Queso` removed entirely. The 3.32.1 unit and orchestrator-level tests pass against `supernova_test` because they exercise `execute_modificar_producto` and `PedidoProductoService.modify_product` directly with hand-crafted `ProcessedIntent` payloads and patched classifiers; they never drive the real HTTP endpoint `POST /comercios/{id}/clientes/{id}/incoming-messages` nor the interactive CLI driver. The defects live in the seam between the orchestrator-level fix and the real HTTP/CLI pipeline, and the test matrix never crossed that seam.

This change reproduces both phrases through the real HTTP endpoint and the interactive CLI, identifies the layer that misbehaves (recognizer, initial orchestrator, pending-context resolver, handler, service, response, HTTP endpoint, or CLI), applies the minimum correction to that layer, and adds a regression matrix that drives the real HTTP/CLI pipeline end-to-end so the prior unit-level coverage is no longer sufficient by itself.

## What Changes

- Run a real-flow reproduction step before any code change: drive the exact two phrases through the running local FastAPI HTTP endpoint and the interactive CLI driver; capture the actual `CustomerResponse.message`, the actual `PedidoProducto` rows, and the actual `ProcessedIntent` outcomes; document the gap between the 3.32.1 unit coverage and the real pipeline. Do not assume which layer is at fault.
- Apply the minimum correction in the layer the reproduction reveals. The change MUST remain inside the seams established by 3.32 and 3.32.1: no DB schema change, no Alembic migration, no new HTTP endpoint, no CLI redesign, no LLM beautification, no extra confirmation turn, no new intent, no broad transaction changes, no lower-level commits, and no second `CustomerResponse` per modification.
- Preserve the 3.32.1 invariants: one replacement command = one `modificar_producto` operation; one `ProcessedIntent`; one `CustomerResponse`; validate source, quantity, and destination before any mutation; one outer transaction owned by `process_incoming_message_transactional`; handler never decomposes into separate `quitar_producto` and `agregar_producto` calls; service never commits, rolls back, flushes, refreshes, expires, or begins.
- Preserve the authoritative quantity rule: when `cantidad` is omitted, the destination quantity equals the current source-line quantity re-read inside the same transaction boundary; when `cantidad` is supplied, that quantity is used for both source removal and destination addition; never default to `1`.
- Preserve the validation-before-mutation rule: every destination validation runs before any source mutation; no commit between source removal and destination addition.
- Preserve the price-snapshot and consolidation rules: existing destination line keeps its stored `precio_unitario`; new destination line reads `current_precio` before the source mutation; consolidation increments the existing destination in place.
- Preserve the corrected pending-context lifecycle: `executed` clears the pending context, definitive `rejected` clears it, `failed` preserves it, raised exceptions propagate for rollback.
- Preserve the deterministic response matrix: executed full transfer, executed partial transfer, executed consolidated, unknown destination (`No encontré el producto de reemplazo. Tu pedido no fue modificado.`), unavailable destination (`El producto no está disponible. Tu pedido no fue modificado.`), excess quantity (`Solo tenés N ... para cambiar. Tu pedido no fue modificado.`). No LLM call, no DB ID exposure, no prompt construction.
- Add real-flow regression tests that drive the actual HTTP endpoint `POST /comercios/{id}/clientes/{id}/incoming-messages` and the interactive CLI driver with the exact two user phrases. The regression matrix MUST assert: the rendered `CustomerResponse.message` is the single modification message; the `PedidoProducto` rows are exactly the expected ones; the `Session.context_type` returns to `None` after a definitive outcome; the source Pedido is unchanged when the destination is rejected; the destination quantity matches the transferred source quantity when the quantity is omitted.
- Keep the existing 3.32.1 unit and orchestrator tests green; do not delete or weaken them. They remain the lower-level safety net.
- Add CLI-order-table regression coverage for the two exact phrases: after Defect 1, the table shows the destination line with `cantidad == 4` and no source line; after Defect 2, the table shows the source line unchanged.
- Document the diagnosis: which layer (recognizer, initial orchestrator, pending-context resolver, handler, service, response, HTTP endpoint, CLI) was responsible for each defect, and why the prior orchestrator-level tests passed while the runtime failed.
- Do NOT sync main specs automatically. Do NOT archive the change automatically. `/opsx:sync` and `/opsx:archive` remain explicit user commands.
