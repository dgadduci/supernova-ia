## Why

Subphase 4.11 delivered an offline calibration runner with a 10-case dataset rooted in synthetic in-memory fixtures. The fixtures cover several `id_comercio` values but none of the existing 10 cases are real database-backed cases for `comercio_id=1`, so the report is not statistically meaningful for any actual commerce. Subphase 4.11.1 must make the calibration usable for `comercio_id=1` by growing the dataset with real database-backed cases covering the 80/20 of representative input shapes, and must define the explicit eligibility inputs (primary metric, required improvement, false-positive tolerance, latency budget) so the runner can emit a real `eligible` / `not_eligible` / `pending` verdict for Subphase 4.12 instead of refusing to invent criteria.

The existing 10 Subphase 4.11 cases are preserved verbatim as they stand today — including their `catalog_scope: "in_memory"` fixtures, their `catalogs[*].entries` lists, and their expected outcomes. They are **not** counted as `comercio_id=1` cases: their `catalog_scope` is `in_memory`, not `commerce_dynamic_database`, and their `id_comercio` values are not 1. They remain in the dataset as the regression baseline but are excluded from the per-commerce minimum.

## What Changes

- Expand `backend/data/product_recognition_calibration_cases.json` to a final total of 30–50 cases inclusive of the 10 preserved Subphase 4.11 cases. The final dataset MUST contain at least 30 evaluable cases for `comercio_id=1`, in addition to the 10 preserved cases for other comercios. The preserved cases for other comercios stay in the dataset and continue to be evaluated, but they are excluded from the `comercio_id=1` minimum.
- Every new `comercio_id=1` case uses `catalog_scope: "commerce_dynamic_database"`, `id_comercio: 1`, and references real `producto`, `producto_presentacion`, `presentacion`, and `producto_alias` rows that exist in the seeded database.
- Cover the 80/20 of representative input shapes for `comercio_id=1`: exact canonical, alias, fuzzy misspelling, colloquial wording, product+presentation, quantity words, ambiguous requests, unknown products, restricted candidate sets, semantically similar products, and cases where fuzzy and vector may disagree.
- Define an explicit, repository-supported inventory step, runnable from the project root, scoped to the new `commerce_dynamic_database` cases with `id_comercio = 1`; it queries that seeded commerce and regenerates or validates only the `seed_refs` entries used by those cases in `backend/data/product_recognition_calibration_cases.json`. The inventory step is the single source of truth for which `producto_presentacion_id` belongs to each such symbolic key. The symbolic keys are opaque and portable; numeric IDs are NEVER used as portable symbolic references.
- Cases reference `expected_producto_presentacion_id` exclusively through the symbolic `seed_refs` map. Runtime code MUST NOT import test infrastructure to resolve the map. The inventory step lives outside the runtime code path and stays under the project's tooling.
- Calibration applies database-backed reference validation only when `catalog_scope == "commerce_dynamic_database"`. For each such case, before evaluating that case, it resolves and validates every `expected_producto_presentacion_id_ref` and validates every `allowed_candidate_ids` / `restricted_candidate_ids` entry against that case's own `id_comercio`. It fails clearly for a missing symbolic reference, a nonexistent resolved or candidate ID, a cross-commerce ID, or an ambiguous symbolic resolution, identifying the case, reference or candidate, offending value, and expected commerce scope.
- For `catalog_scope: "in_memory"`, calibration does not validate candidate IDs against the seeded database, does not force `id_comercio=1`, and does not reinterpret fixture IDs as production database IDs. The existing embedded-catalog validation and evaluation path remains unchanged.
- Add an optional `eligibility` block to the calibration dataset carrying `primary_metric`, `required_improvement`, `false_positive_tolerance`, and `latency_budget_ms_p95`. The runner reads it from the dataset when no explicit `eligibility` argument is supplied; existing tests continue to pass `eligibility` directly.
- Bump the dataset `schema_version` to `3` to mark the new optional `eligibility` block and the new case coverage. The runner accepts `schema_version` `2` and `3`; existing `v2` datasets remain valid.
- Preserve the existing 10 cases verbatim (no removal, no mutation of expected outcomes), the Subphase 4.11 calibration runner, the deterministic grid, the JSON report schema, the `Fuzzy baseline comparison and eligibility` requirement, the local CLI surface, and the rule that fuzzy remains authoritative and hybrid remains observational.
- Add focused tests for: dataset schema (presence and types of `eligibility` block plus existing fields); scope-aware reference validation that validates all expected and candidate references against each `commerce_dynamic_database` case's own `id_comercio`; preservation of the 10 verbatim `in_memory` cases without seeded-database candidate validation, forced commerce scope, or fixture-ID reinterpretation; category coverage of the added cases; eligibility evaluation from the dataset `eligibility` block; deterministic calibration output for the expanded dataset; and explicit failure messages for missing / nonexistent / cross-commerce / ambiguous references.
- After implementation, run the inventory step, run embedding seeding if required, execute the calibration CLI for `comercio_id=1`, and report case count, category counts, fuzzy metrics, hybrid metrics, selected policy, infrastructure failures, and eligibility status with reasons. Do not run `/opsx:sync` or `/opsx:archive`.

## Capabilities

### New Capabilities

- `expand-product-recognition-calibration-dataset-4-11-1`: offline calibration dataset expansion with real database-backed cases for `comercio_id=1`, dataset-carried eligibility inputs, and a repository-supported inventory step for the `seed_refs` map.

### Modified Capabilities

- `calibrate-hybrid-product-recognition-4-11`: add a new requirement that the calibration dataset MAY carry an optional `eligibility` block with `primary_metric`, `required_improvement`, `false_positive_tolerance`, and `latency_budget_ms_p95`, and that the runner reads it when no explicit `eligibility` argument is supplied. Bump accepted `schema_version` to `2` and `3`. No existing requirement or scenario is removed or weakened.

## Impact

- `backend/data/product_recognition_calibration_cases.json` — final total of 30–50 cases inclusive of the 10 preserved Subphase 4.11 cases, with at least 30 evaluable cases for `comercio_id=1`; the 10 preserved cases remain verbatim and are excluded from the `comercio_id=1` minimum. Adds an optional `eligibility` block, bumps `schema_version` to `3`, and uses a top-level `seed_refs` map of opaque symbolic keys regenerated or validated by the inventory step.
- `backend/scripts/calibration_inventory.py` (new) — repository-supported inventory step scoped exclusively to regenerating and validating `seed_refs` for the new `commerce_dynamic_database` cases with `id_comercio=1`. It queries the seeded database for `id_comercio = 1`, resolves that map in regenerate or validate mode, and exits non-zero with a clear message when a required key is missing, nonexistent, cross-commerce, or ambiguous. It does not inspect or reinterpret the preserved `in_memory` cases. The script lives outside the runtime code path and MUST NOT be imported by runtime modules.
- `backend/services/product_recognition_calibration_policy.py` — `validate_dataset` accepts `schema_version` `3` and validates the optional `eligibility` block (numeric types, allowed primary metric values, non-negative latency budget). Existing `v2` validation behavior is preserved.
- `backend/services/product_recognition_calibration_runner.py` — `ProductRecognitionCalibrationRunner.run` consumes `dataset["eligibility"]` when no explicit `eligibility` argument is supplied. Latency budget is read from `latency_budget_ms_p95` and converted to milliseconds for the existing gate. Only `commerce_dynamic_database` cases receive database-backed reference validation: every expected reference and allowed/restricted candidate is checked against that case's own `id_comercio`, with clear missing, nonexistent, cross-commerce, and ambiguous failures before that case is evaluated. The 10 preserved `in_memory` cases stay on the existing embedded-catalog path without seeded-database candidate validation, forced commerce scope, or fixture-ID reinterpretation. No behavior change when the eligibility argument is supplied explicitly. The runner MUST NOT import test infrastructure to resolve `seed_refs`.
- `backend/cli/calibrate_product_recognizer.py` — no changes required; the CLI already passes no `eligibility` argument and the runner will read it from the dataset.
- `backend/tests/` — focused tests for `schema_version` `3`, dataset `eligibility` validation, runner consumption of dataset `eligibility`, scope-aware database reference validation for each new `commerce_dynamic_database` case against its own `id_comercio`, preservation of the 10 verbatim `in_memory` cases on their embedded-catalog path, category coverage of the expanded set, deterministic calibration output, and explicit failure messages for missing / nonexistent / cross-commerce / ambiguous references.
- Affected runtime contracts: none. Fuzzy remains the authoritative runtime recognizer; `PRODUCT_RECOGNIZER_MODE=hybrid` is not activated; handlers, resolvers, pending contexts, intents, orders, responses, persistence contracts, HTTP endpoints, canonical specs, and runtime settings are not touched. The inventory step is a tool script, not a runtime dependency.
- Affected dependencies: existing collaborators (`FuzzyProductRecognizer`, the embedding client, `ProductPresentationVectorSearchService`) are reused through their current protocols. No new external libraries, no schema migration, no HTTP endpoint, no production persistence contract change. The inventory step uses the existing SQLAlchemy session factory and the existing seed data; it does not introduce a new persistence path.
