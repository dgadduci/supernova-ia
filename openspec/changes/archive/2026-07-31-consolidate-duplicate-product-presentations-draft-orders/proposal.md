## Why

Within a `Pedido` in state `borrador`, the `agregar_producto` handler always inserts a new `PedidoProducto` row through `PedidoProductoService.add`, even when the same `(id_pedido, id_producto_presentacion)` pair already exists. Adding `2 empanadas de verdura`, then `1 empanada de verdura`, then `4 empanadas de verdura` produces three separate rows with quantities `2`, `1`, and `4` instead of one consolidated row with quantity `7`. The CLI order-table regression test from subphase 3.30.2 surfaced this defect: the displayed table shows three rows for the same product-presentation because persistence contains three rows, not because of any renderer-side grouping. Subphase 3.30.3 fixes the persistence path so the authoritative domain invariant — *at most one active `PedidoProducto` per `(id_pedido, id_producto_presentacion)` in a draft pedido* — is enforced in the service, and any existing duplicates in `supernova` / `supernova_test` are consolidated by a hand-written Alembic migration before the new unique constraint is applied.

## What Changes

- **`PedidoProductoService.add_or_increment` becomes the new entry point for the `agregar_producto` handler.** The service looks up an existing `PedidoProducto` belonging to the same `(pedido_id, producto_presentacion_id)`; if one exists it increments `cantidad` and preserves the original `precio_unitario` snapshot, otherwise it snapshots the current catalog price and inserts a new row. The legacy `PedidoProductoService.add` is kept for the `POST /pedidos/{pedido_id}/productos` HTTP endpoint, which retains its create-only semantics — duplicates from HTTP are still rejected as today (the existing `PedidoProducto`/`pedido` modules expose only update/delete for an existing line item, so the HTTP path never creates a duplicate today).
- **`PedidoProductoRepository.get_by_pedido_and_producto_presentacion(pedido_id, producto_presentacion_id) -> PedidoProducto | None`** is added so the service can perform a single bounded lookup without loading the full pedido. The repository never commits, never flushes (the service flushes only if its convention requires it), and never loads unrelated line items.
- **`execute_agregar_producto` delegates to `PedidoProductoService.add_or_increment`** instead of `add`. The handler's translation rules and `executed` / `rejected` / `failed` semantics are unchanged: a missing pedido, a non-borrador pedido, an unknown product-presentation, or a missing `Precio` row is still rejected; a quantity `< 1` is still rejected; a raised exception is still mapped to `failed`; a successful call still returns `executed`. The handler does not decide whether to insert or increment — that decision lives in the service.
- **The `ProcessedIntent` returned by the handler carries enough result data for the response builder.** `resolved_data` is augmented with `cantidad_agregada` (the quantity added in this operation) and `cantidad_final` (the resulting quantity on the line). A new boolean `linea_creada` distinguishes "newly created" from "incremented" — the response builder may or may not surface this distinction; the contract requires only that the data is available. The handler does not mutate the intent's `requirements` or `candidate_ids`.
- **`build_agregar_producto_response` uses the new resolved_data when present** but remains backward compatible: when `cantidad_agregada` is absent the builder falls back to the existing `cantidad` field, so the existing successful response messages continue to work. The singular / plural phrasing remains driven by `cantidad` (the quantity on the line after the operation), not by `cantidad_agregada` — the contract from subphase 3.27 is preserved verbatim.
- **A new Alembic migration hand-writes the duplicate-consolidation step before the unique constraint.** The migration runs a single `SELECT` to identify all `(pedido_id, producto_presentacion_id)` groups with more than one row, sums the quantities into one surviving row per group, deletes the duplicates, then creates the unique constraint `uq_pedido_producto_presentacion` on `(id_pedido, id_producto_presentacion)`. The migration strategy is deterministic: keep the lowest `id` per group, sum quantities, copy the lowest row's `precio_unitario` and `observaciones` to the surviving row, update the surviving row's `cantidad`, and delete the rest. The migration does not silently delete data without review: the change's design report enumerates the rows that would be consolidated against `supernova` and `supernova_test` before the migration runs.
- **A model-level `UniqueConstraint("id_pedido", "id_producto_presentacion", name="uq_pedido_producto_presentacion")` is added to `PedidoProducto.__table_args__`** so autogenerate keeps the invariant in the schema. The Alembic migration creates the same constraint at the database level. The existing `cantidad_positiva` `CheckConstraint` is unchanged.
- **`backend/alembic/env.py` is unchanged** (the `PedidoProducto` import already exists from subphase 2.14).
- **A new focused test module `backend/tests/test_consolidate_duplicate_product_presentations.py`** covers the full consolidation contract — first addition creates a row, second addition increments, multiple identical additions keep one row, different presentations stay separate, same presentation in different pedidos stays separate, price snapshot is preserved on increment, new line still snapshots current price, invalid quantity rejected, non-draft pedido rejected, raised exception propagates and rolls back, full HTTP end-to-end through `/incoming-messages` produces one row with summed quantity, ambiguous-selection + later repeat increments the existing line, the CLI order-table regression test from subphase 3.30.2 passes against the consolidated persistence, and `quitar_producto` (subphase 3.31) still decrements / deletes the single consolidated line.

## Capabilities

### New Capabilities

_None._ The change refines an existing domain invariant inside the established `pedido_producto` / `agregar_producto` stack; no new external capability is introduced.

### Modified Capabilities

- `pedido-producto-api`: the service-layer consolidation logic is added behind the existing `POST /pedidos/{pedido_id}/productos` endpoint (which keeps its create-only HTTP semantics); a new repository lookup is added; the model gains a `UniqueConstraint("id_pedido", "id_producto_presentacion")` so duplicate rows are rejected at the database level for any future caller that bypasses the service.
- `agregar-producto-handler`: `execute_agregar_producto` delegates to `PedidoProductoService.add_or_increment` and threads `cantidad_agregada` / `cantidad_final` / `linea_creada` through `resolved_data`. Translation rules, status outcomes, and the no-database-access contract are unchanged.
- `agregar-producto-customer-response`: the response builder reads `cantidad_agregada` / `cantidad_final` from `resolved_data` when present and falls back to the existing `cantidad` field otherwise. Phrasing rules from subphase 3.27 are preserved; the executed message continues to reflect the quantity added.
