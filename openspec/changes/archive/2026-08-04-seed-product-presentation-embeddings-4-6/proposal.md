## Why

The hybrid recognizer stack (Phase 4) has shipped every primitive except the persistence evolution that turns the pure `ProductEmbeddingDocumentBuilder` into per-document embeddings with content-addressed idempotency: Subphase 4.5 produces a deterministic `canonical` / `description` / `alias` / `combined` document list per `producto_presentacion`, Subphase 4.4 supplies the validated Ollama client, Subphase 4.3 persists embeddings keyed by `(id_producto_presentacion, modelo)` — but that aggregate identity collapses every document into one row, hides which document a vector represents, forces a full re-embedding on any catalog change, and has no notion of staleness or inactivity. Subphase 4.6 must therefore evolve the persistence boundary to per-document rows, introduce a small status state machine (`pending` / `ready` / `failed` / `stale` / `inactive`) with explicit reactivation paths, enforce data integrity through PostgreSQL `CHECK` constraints, and expose a CLI that indexes the catalog through the existing builder while honoring hash-based idempotency at the document level.

## What Changes

- Evolve the existing `producto_presentacion_embeddings` table through a new hand-written Alembic migration that adds the missing per-document columns (`source_type`, `source_record_id`, `source_text`, `normalized_text`, `content_hash`, `embedding_status`, `activo`, `last_error`), makes `vector` nullable (non-ready states may not have a vector), drops the legacy `(id_producto_presentacion, modelo)` aggregate uniqueness rule, truncates the placeholder dev/test rows from Subphase 4.3 (single explicit strategy — no pointless backfill followed by truncate), and creates two PostgreSQL partial unique indexes (one for `(id_producto_presentacion, modelo, source_type) WHERE source_record_id IS NULL` covering canonical / description / combined, and one for `(id_producto_presentacion, modelo, source_type, source_record_id) WHERE source_record_id IS NOT NULL` covering alias rows).
- Add PostgreSQL `CHECK` constraints at the table level (seven total):
  - `source_type_chk`: `source_type` drawn from the closed set `canonical | description | alias | combined`;
  - `source_record_id_alias_chk`: `source_record_id` non-null when `source_type = 'alias'`, null otherwise;
  - `ready_vector_chk`: `vector` non-null when `embedding_status = 'ready'`;
  - `content_hash_chk`: `content_hash` matches `^[0-9a-f]{64}$` (lowercase 64-character hex);
  - `source_text_nonempty_chk` and `normalized_text_nonempty_chk`: `source_text` and `normalized_text` are non-empty after trimming;
  - `embedding_status_chk`: `embedding_status` drawn from the closed set `pending | ready | failed | stale | inactive`.
- Define `EmbeddingStatus` as a `str, enum.Enum` whose values ARE the lowercase strings (`'pending'`, `'ready'`, `'failed'`, `'stale'`, `'inactive'`) and store it in a `String(32)` column. The closed set is enforced by the table-level `embedding_status_chk` (`CHECK (embedding_status IN ('pending','ready','failed','stale','inactive'))`). There is exactly one database representation: the lowercase string. No SQLAlchemy-side `values_callable` shim, no PostgreSQL `CREATE TYPE`, no uppercase-to-lowercase translation. The Python enum and the PostgreSQL CHECK share the same value space.
- Extend the SQLAlchemy `ProductoPresentacionEmbedding` model with the new columns, the table-level `CHECK` constraints, and the two partial unique indexes. `vector` becomes `nullable=True`.
- Refactor `ProductoPresentacionEmbeddingRepository` so it performs only SQLAlchemy reads and writes (`find_by_document`, `list_by_producto_presentacion_and_model`, `list_by_comercio`, `list_by_producto`, `list_by_producto_presentacion`, `insert_document`, `update_document`, `mark_status`). The repository does NOT compute hash equality, does NOT decide between created / updated / unchanged / failed, and does NOT own commit / rollback / close / begin. `update_document(row, *, source_text, normalized_text, content_hash, vector, embedding_status, activo, last_error)` persists the complete document metadata (`source_text`, `normalized_text`, `content_hash`, `vector`, `embedding_status`, `activo`, `last_error`, `fecha_ultima_modificacion`); reconciliation decisions remain in the service / indexer.
- Move the hash-based idempotency decision to `ProductoPresentacionEmbeddingService` (or directly to the indexer, where the data is in scope). The service exposes `create_or_update_document(document, vector, *, modelo, force=False)` that:
  - loads the existing row by the document tuple `(id_producto_presentacion, modelo, source_type, source_record_id)`;
  - returns `DocumentReconciliationOutcome.UNCHANGED` only when ALL of the following are true: the stored `content_hash` equals the incoming `content_hash`; `embedding_status == 'ready'`; `activo == True`; the stored `vector` is present and has the configured dimension; `force == False`. When all five conditions hold, no write is issued, no Ollama call is issued, and no `fecha_ultima_modificacion` advance occurs;
  - otherwise, when a row already exists, delegates to `repository.update_document(...)` to rewrite `source_text`, `normalized_text`, `content_hash`, `vector`, set `embedding_status='ready'`, set `activo=True`, clear `last_error`, and advance `fecha_ultima_modificacion`, then returns `DocumentReconciliationOutcome.UPDATED`. This path covers `failed → ready`, `stale → ready`, `inactive → ready`, and `--force` with an unchanged hash;
  - when no row exists, delegates to `repository.insert_document(...)` and returns `DocumentReconciliationOutcome.CREATED`;
  - delegates the actual write to the repository;
  - never calls `commit`, `rollback`, `close`, or `begin`.
- Add an explicit `record_failed_document(document, error_message, *, modelo)` operation on the service for embedding failures. Required behavior:
  - when no row exists for the document tuple, `repository.insert_document(...)` is called with `vector=NULL`, `embedding_status='failed'`, `activo=True`, and a sanitized `last_error` derived from the supplied message;
  - when a row already exists, `repository.update_document(...)` is called to persist the document metadata, `embedding_status='failed'`, `activo=True`, and the sanitized `last_error` while preserving the previous `vector` and `fecha_alta`;
  - the operation increments only the `failed` counter at the indexer level; it never increments a successful `created` or `updated` counter;
  - a batch failure applies this operation to every affected document (every document in the failed batch), so each affected document ends up in `embedding_status='failed'` with `last_error=<safe client message>`.
- Define the status state machine with explicit reactivation paths. Allowed transitions (everything else is rejected by `mark_status` with `InvalidEmbeddingStatusTransition`):
  - `pending → ready | failed | inactive`;
  - `ready → failed | stale | inactive` (and `ready → ready` is an idempotent no-op);
  - `failed → ready | failed | stale | inactive` (recovery via a fresh successful embedding, or preservation as obsolete / inactive when the catalog changes);
  - `stale → ready | failed | inactive` (recovery when the document becomes generated again, preservation as inactive when the catalog changes);
  - `inactive → ready | failed | stale` (recovery when the catalog is re-activated, preservation as obsolete when the builder no longer produces the document);
  - `stale` and `inactive` are NOT permanently terminal; they preserve the row's vector and timestamps and may transition back to `ready` when the document is regenerated or the catalog is re-activated.
- Add `ProductoPresentacionEmbeddingIndexer` that loads every applicable `producto_presentacion` (active and inactive, scoped by comercio / producto / producto_presentacion filters), and for each presentation:
  - detects the inactive-catalog chain first. If any parent (`Producto`, `CategoriaProducto`, `Presentacion`, `ProductoPresentacion`) has `activo = false`, the indexer loads the existing rows, transitions every row to `inactive` through the service, and does NOT run the pure builder, does NOT call Ollama, does NOT insert / update new rows for that presentation.
  - if the catalog chain is active, runs the pure `ProductEmbeddingDocumentBuilder` to obtain the deterministic documents.
  - classifies each document against the existing row through the service's hash-based idempotency (`create_or_update_document(document, vector, *, modelo=settings.embedding_model, force=force)`):
    - `unchanged` is returned only when ALL of these are true: the stored `content_hash` equals the incoming `content_hash`; `embedding_status == 'ready'`; `activo == True`; the stored `vector` is present and has the configured dimension; `force == False`. When all five conditions hold, the indexer does NOT call Ollama, does NOT rewrite the vector, does NOT advance `fecha_ultima_modificacion`, and does NOT call `flush`. Source-text differences that produce the same `normalized_text` (and therefore the same `content_hash`) are deliberately treated as irrelevant for reindexing; the 4.5 hash contract guarantees deterministic equality on `normalized_text`, but the indexer does NOT claim that the embedding model is guaranteed to return the same vector for the same `normalized_text`.
    - `updated` is returned when a row exists but ANY of the unchanged conditions is false: the hashes differ, the row is in `failed` / `stale` / `inactive`, `activo` is `False`, the stored `vector` is missing or dimension-mismatched, or `force == True`. The indexer sends `source_text` (not `normalized_text`) through the embedding client in a bounded batch, calls `service.create_or_update_document(...)`, and the service delegates to `repository.update_document(...)` which persists the complete document metadata, sets `embedding_status='ready'`, sets `activo=True`, clears `last_error`, and advances `fecha_ultima_modificacion`.
    - `created` is returned when no row exists. The indexer sends `source_text` through the embedding client in a bounded batch, calls `service.create_or_update_document(...)`, and the service delegates to `repository.insert_document(...)` with `embedding_status='ready'`, `activo=True`, `last_error=NULL`.
    - `--force` is passed explicitly to `create_or_update_document` so the unchanged branch is bypassed for every applicable document.
  - marks obsolete documents (those the builder no longer produces for an active catalog chain) as `stale` through the service. The vector and timestamps are preserved.
- Define batching precisely:
  - the indexer collects every document whose status requires generation into one logical batch;
  - calls `embedding_client.embed_documents(texts)` exactly once for that batch;
  - preserves the positional mapping between the returned vectors and the documents by index;
  - if the batch raises `EmbeddingClientError`, every affected document transitions to `failed` with `last_error=<safe client message>` and the indexer continues with the next safe batch (the next presentation's documents).
- Add `ProductoPresentacionEmbeddingSeeder` that wraps the indexer and returns a `SeedingResult` carrying `(created, updated, unchanged, stale, inactive, failed)` aggregate counts plus a per-presentation `SeedingOutcome` list. The seeder does NOT call `session.commit()`, `session.rollback()`, or `session.close()`. The CLI is the only owner of those calls.
- Add `backend/scripts/seed_product_presentation_embeddings.py` with `--comercio-id`, `--producto-id`, `--producto-presentacion-id`, `--force`, `--dry-run`, `--batch-size`. The CLI:
  - opens `_SessionLocal()`, instantiates the indexer with the project's loaded `Settings` and an `OllamaEmbeddingClient(settings)`;
  - when `--batch-size` is supplied, calls `dataclasses.replace(settings, embedding_batch_size=args.batch_size)` and passes the resulting frozen `Settings` to the `OllamaEmbeddingClient`. The client's constructor is NOT modified — it stays `(settings, transport=None, clock=None)`.
  - calls `seeder.run(session)` and prints the summary.
  - `--dry-run` is strictly read-only. When `dry_run=True`:
    - the catalog is projected and every document is classified through the same hash-based idempotency path the real run uses, so the planned `created`, `updated`, `unchanged` totals are reported;
    - planned `stale` and `inactive` outcomes are also classified (so the summary reports them);
    - `mark_stale` is NOT called;
    - `mark_inactive` is NOT called;
    - NO row is inserted, updated, or marked — `repository.insert_document`, `repository.update_document`, and `repository.mark_status` are NOT called;
    - `session.flush()` is NOT called;
    - `embedding_client.embed_documents(...)` is NOT called — Ollama is never reached;
    - `session.commit()` is NOT called; the session is closed in the `finally` block without a prior commit.
- Use the exact change identifier `seed-product-presentation-embeddings-4-6` everywhere — in paths, scripts, and `openspec validate`. There is exactly one identifier.
- Run only the minimum tests required to verify migration integrity, document-level uniqueness, initial indexing, hash-based idempotency, semantic updates, alias stale / inactive behavior, failure handling, commerce isolation, dry-run behavior, and the directly affected persistence (4.3), embedding-client (4.4), and builder / normalization (4.5) surfaces. Do NOT require the full `api_smoke.py` or unrelated fuzzy-recognizer suites unless a focused test reveals a regression there.
- Repositories and services MUST NOT call `commit`, `rollback`, `close`, or `begin`. SQLAlchemy `flush()` is permitted (it writes rows to the session's pending state without committing). The CLI is the only owner of `session.commit()`, `session.rollback()`, and `session.close()`.
- Transaction behavior at the CLI:
  - a completed real run that finished with recoverable embedding failures persists the `failed` rows (with sanitized `last_error`), commits once via `session.commit()`, and exits with code `1`. The run is treated as successful from a persistence standpoint; the non-zero exit code surfaces the recoverable failures to the operator;
  - a run whose failure is an unhandled persistence or integrity error (e.g. `SQLAlchemyError`, `IntegrityError` not translated to `DuplicateEmbeddingDocument`) does NOT commit; the CLI calls `session.rollback()` once, re-raises the exception, and exits with code `1`;
  - a `--dry-run` never commits. The CLI opens the session, runs the projection and classification without persisting, closes the session in `finally`, and exits with code `0`.
- No vector similarity search, no HNSW or IVFFlat, no admin endpoint, no automatic catalog-change hook, no hybrid recognizer wiring, no fuzzy recognizer change, no Subphase 4.7.

## Capabilities

### New Capabilities

- `product-presentation-embedding-indexing`: per-document embedding indexing through the existing builder, with hash-based idempotency, status state machine (with reactivation paths), stale / inactive preservation, commerce-scoped filters, dry-run classification, and a CLI runner that owns the outer transaction.

### Modified Capabilities

- `producto-presentacion-embeddings`: evolve the persistence boundary from one-aggregate-row-per-presentation to one-row-per-semantic-document; add `source_type`, `source_record_id`, `source_text`, `normalized_text`, `content_hash`, `embedding_status`, `activo`, `last_error`; make `vector` nullable; replace the aggregate uniqueness rule with two PostgreSQL partial unique indexes; add seven PostgreSQL table-level `CHECK` constraints: `source_type_chk`, `source_record_id_alias_chk`, `ready_vector_chk`, `content_hash_chk`, `source_text_nonempty_chk`, `normalized_text_nonempty_chk`, `embedding_status_chk`; expose per-document repository methods (read / write only — hash comparison and reconciliation stay in the service or indexer); the repository `update_document(...)` operation persists the complete document metadata (`source_text`, `normalized_text`, `content_hash`, `vector`, `embedding_status`, `activo`, `last_error`, `fecha_ultima_modificacion`); expose a status state machine with the authoritative transitions (`pending → ready | failed | inactive`, `ready → failed | stale | inactive`, `failed → ready | failed | stale | inactive`, `stale → ready | failed | inactive`, `inactive → ready | failed | stale`) plus `ready → ready` as an idempotent no-op; expose `record_failed_document(...)` for embedding failures (insert with `vector=NULL` when missing, update with metadata + sanitized `last_error` while preserving the previous `vector` when existing); preserve stale and inactive documents instead of deleting them.
