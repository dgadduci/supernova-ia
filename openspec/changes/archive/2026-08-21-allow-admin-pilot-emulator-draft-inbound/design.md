# Design: Emulator inbound on an active draft order

## Decision

Reuse the existing Admin/Pilot detail emulator route and the existing
`load_active_emulator_target` seam. The only eligibility change is to accept
`EstadoPedido.BORRADOR` when the exact Pedido/Session/client/commerce identity
and all existing operational guards are valid.

The route continues to send an authenticated command to the standalone
emulator. It does not call the T-C webhook, coordinator, worker or dispatcher
directly, and it does not create or transition business records.

## Exact target contract

The target loader SHALL require:

1. The selected Pedido exists.
2. The selected Pedido is associated with a Session.
3. `session.id_pedido == pedido.id`.
4. The Session is `ACTIVA`.
5. The Session's client and commerce match the Pedido's loaded associations.
6. The exact commerce has an active dedicated Twilio channel.
7. The commerce is available and has an active T-C installation before the
   route invokes the emulator.

The draft state is the only newly eligible Pedido state. Existing eligibility
for non-draft detail targets must not be widened or narrowed accidentally.

## Request sequence

```text
Admin browser
  -> POST /admin/pilot/orders/{pedido_id}/emulator-test
  -> target validation including active draft
  -> twilio_emulator /internal/emulator/inbound
  -> T-C webhook signature validation
  -> NovaOrders provider coordinator
  -> existing provider worker
  -> existing draft order processing and outbound staging
  -> existing T-C outbound command
  -> twilio_emulator Messages API
  -> existing status polling for the same pedido/session
```

For a second or later message, the provider receipt identity remains the
synthetic inbound identifier generated by the emulator. Existing duplicate
receipt handling, pending context, worker leases, retries and outbox identity
remain authoritative.

## Status projection

The existing `emulator-test/status` route should use the same exact target
identity for a draft as for a non-draft order. It may report accepted/pending,
processed or sent using the existing bounded receipt/outbox projection. It
must not create state, search for another active Session or return raw provider
payloads.

## UI behavior

The detail page should say that `Enviar por Twilio Emulator` can be used for
an active draft as well as the existing eligible order states. The current
local-only action remains separate. The browser transcript and status result
remain volatile, escaped and bounded.

## Failure behavior and safety

Every existing rejection branch remains fail-closed. A draft with a closed or
detached Session, unavailable commerce, missing dedicated channel, inactive
installation or disabled emulator is rejected before any emulator request.
There is no fallback to the local path or real Twilio.

## Concurrency and business invariants

The change does not create a second active Session or a successor Pedido. Two
distinct accepted inbound messages may process sequentially through the same
active draft Session, subject to the existing provider receipt and worker
semantics. The implementation must not loosen commerce isolation, pending
candidate boundaries or transaction ownership.

## Testing strategy

Use focused service/route tests with a fake emulator client and existing test
fixtures. Assert draft acceptance, exact identity, server-side addresses,
single downstream call, no route-owned transaction completion, status scoping,
consecutive submissions and preservation of non-draft/local behavior. Add no
Railway, Twilio or live-worker dependency to unit tests.
