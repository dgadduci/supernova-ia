## Why

Subphase 4.11.3 archived at `openspec/changes/archive/2026-08-04-subphase-4-11-3-calibration-evaluation-mismatch/` closed the dataset / seed / identifier defect surface. Subphase 4.11.3 proved that the evaluator and the expected identifiers are valid for every `commerce_dynamic_database` case: the seven dataset / seed / identifier mismatch categories all sit at `0` in the post-fix `mismatch_category_counts` aggregate. Subphase 4.11.3 did **not** prove that the runtime fuzzy recognizer itself fails for the remaining 29 fuzzy cases — it proved only that the offline calibration runner is the broken component.

The immediate demonstrated defect is that `ProductRecognitionCalibrationRunner.run` (`backend/services/product_recognition_calibration_runner.py:636`) hands `FuzzyProductRecognizer.recognize(...)` an empty catalog for every `catalog_scope: "commerce_dynamic_database"` case (`dataset["catalogs"][fixture].entries` is `[]` by design under the Subphase 4.11.1 contract), while the vector search on the same case at `runner.py:654-660` is correctly given `allowed_candidate_ids`. The fuzzy recognizer therefore returns `unknown` regardless of whether the runtime would have found the candidate, the hybrid ranking inherits the empty fuzzy ranking, and the calibration cannot distinguish a real fuzzy defect from a calibration-environment defect.

The fix is calibration-environment only: the runner must hand the fuzzy recognizer the **full runtime-compatible commerce catalog** for the case's commerce — i.e. every commerce-scoped `producto_presentacion` entry that the real runtime catalog assembly would provide, including entries whose availability flags are `false` — exactly as the runtime call sites (`backend/intents/context/product_selection_context_resolver.py:165` and siblings) hand the same recognizer the runtime catalog. `allowed_candidate_ids` and `restricted_candidate_ids` are evaluation constraints applied **after** recognition, never inputs to catalog construction. Inactive and unavailable entries remain present in the catalog with their original flags (`activo`, `producto_activo`, `presentacion_activo`, `disponible`) and are routed by the recognizer's existing `disponibles` / `encontrados_no_disponibles` split (`backend/recognizers/product_recognizer.py:543-561`). Only the cases that still fail after this correction may be classified as genuine fuzzy recognizer failures and become the documented future work; the 29 cases currently bucketed under `real_fuzzy_recognizer_failure` are not, on the current evidence, proven customer-facing runtime failures.

## What Changes

- Load (or persist into the dataset) a deterministic `commerce_catalog_inventory` block keyed by `id_comercio`. Each value is the full runtime-compatible commerce catalog — all commerce-scoped `producto_presentacion` entries returned by the real runtime catalog assembly, with the same shape that `_preparar_catalogo` (`backend/recognizers/product_recognizer.py:244-262`) consumes (`producto_presentacion_id`, `producto_id`, `presentacion_id`, `categoria_id`, `producto_nombre`, `categoria_nombre`, `presentacion_codigo`, `presentacion_descripcion`, `activo`, `producto_activo`, `presentacion_activo`, `disponible`). Inactive and unavailable entries (where any of `activo`, `producto_activo`, `presentacion_activo`, `disponible` is `false`) remain present with their original flags and are routed by the recognizer's existing `disponibles` / `encontrados_no_disponibles` split. Entries are deterministically sorted by `producto_presentacion_id` ascending.
- Cache the per-commerce catalog once per calibration run. The runner loads the catalog for a `commerce_id` on the first case that requests it and reuses the same list for every subsequent case at that commerce — exactly one catalog object per commerce, never one per case, never one per call.
- Pass the cached full-commerce catalog to the fuzzy recognizer for every `catalog_scope: "commerce_dynamic_database"` case. `allowed_candidate_ids`, `restricted_candidate_ids`, `expected_decision`, `expected_producto_presentacion_id`, `expected_producto_presentacion_id_ref`, and any other case label MUST NOT influence the catalog construction. The 11 preserved `catalog_scope: "in_memory"` cases continue to use their embedded `catalogs[*].entries` unchanged.
- Apply `allowed_candidate_ids` and `restricted_candidate_ids` strictly in the evaluator, after the fuzzy recognizer returns its candidates. The evaluator accepts a fuzzy candidate as in-boundary iff its `producto_presentacion.id` is in `allowed_candidate_ids`, and flags a candidate as a boundary violation iff its id is in `restricted_candidate_ids`; the vector-search boundary check at `runner.py:654-660` is preserved unchanged.
- Persist a parallel `commerce_catalog_fingerprint` block keyed by `id_comercio` carrying a SHA-256 fingerprint of the canonical JSON of that commerce's catalog entries. The persisted `commerce_catalog_inventory` block (when present) and its `commerce_catalog_fingerprint` are reproducible evidence of the database snapshot the change was authored against; they are NOT the runtime source of truth. At calibration time, the runner MUST load the full runtime-compatible catalog from PostgreSQL once per `id_comercio`, compute its fingerprint, compare that fingerprint against the persisted `commerce_catalog_fingerprint[<id_comercio>]`, and refuse to start with `StaleCommerceCatalogError` (CLI returns non-zero, no report emitted) on mismatch. The freshly loaded DB catalog — not the persisted inventory — is what is handed to the recognizer and cached for every case at that commerce. The existing `seed_refs` map, the existing `inventory_fingerprint` derivation at `runner.py:612-628`, and the existing stale-`seed_refs` guard are preserved unchanged.
- Re-run the full calibration against the unchanged dataset and reclassify every previously-`real_fuzzy_recognizer_failure` / `real_hybrid_recognizer_failure` case using the Subphase 4.11.3 taxonomy. The proposal does **not** promise that all 29 cases will disappear — it promises that the empty-catalog defect is eliminated, that the recognizer receives a faithful full-commerce catalog, and that label leakage is impossible. Cases that still fail are evidence-based residual failures, not calibration-environment artefacts.
- Preserve fuzzy mode as the authoritative runtime recognizer; `PRODUCT_RECOGNIZER_MODE` is not changed; no embedding model, Ollama configuration, vector data, hybrid ranking, recognizer contract, handler, resolver, HTTP contract, order transaction, or persistence contract is modified. No latency budget, threshold, weight, score-gap, alias, token, segmenter, or filter is touched.

## Capabilities

### New Capabilities

(none — this change is a calibration-environment defect correction that reuses the existing calibration surface; no new capability is introduced.)

### Modified Capabilities

- `product-recognizer`: add a Requirement that the fuzzy recognizer, when invoked against a `commerce_dynamic_database` calibration case, MUST receive the full runtime-compatible commerce catalog (every commerce-scoped `producto_presentacion` entry returned by the real runtime catalog assembly for that `id_comercio`, regardless of `allowed_candidate_ids`, `restricted_candidate_ids`, expected decision, expected product IDs, or any other expected-case label), and that no expected-case field MAY be used to narrow the catalog. Add Scenarios pinning the full-commerce catalog (entry count equals the commerce's full runtime-compatible `producto_presentacion` count; entries are sorted by `producto_presentacion_id`; the catalog is identical across cases at the same commerce; changing `allowed_candidate_ids` does not change the catalog; changing `expected_producto_presentacion_id` does not change the catalog; restricted candidates remain present in the catalog and are evaluated post-recognition; entries from another commerce are absent; inactive and unavailable entries remain present with their original flags and are routed by the recognizer's existing `disponibles` / `encontrados_no_disponibles` split).
- `calibrate-hybrid-product-recognition-4-11`: add a Requirement that the calibration runner MUST load the per-commerce catalog from PostgreSQL once per calibration run (the freshly loaded catalog is the runtime source of truth) and reuse it for every `commerce_dynamic_database` case at that commerce; MUST pass the same full catalog to the observation step and the prediction step; MUST NOT consult `allowed_candidate_ids`, `restricted_candidate_ids`, `expected_decision`, or `expected_producto_presentacion_id` when assembling the catalog; MUST apply `allowed_candidate_ids` and `restricted_candidate_ids` only in the evaluator, after recognition. Add Scenarios covering per-commerce caching (fresh DB catalog loaded exactly once per commerce, not once per case), unchanged in-memory catalog behavior for the 11 preserved cases, preserved vector-search boundary check, preserved diagnostic surface from Subphase 4.11.3, and `commerce_catalog_fingerprint` refusal on stale catalog (the fresh DB fingerprint MUST equal `commerce_catalog_fingerprint[<id_comercio>]`).
- `expand-product-recognition-calibration-dataset-4-11-1`: add a Requirement that the dataset MAY carry an optional top-level `commerce_catalog_inventory` block (`dict[id_comercio, list[CatalogEntry]]`) and a parallel `commerce_catalog_fingerprint` block (`dict[id_comercio, str]`), without bumping `schema_version`, without weakening the 11 + 36 case count, the category coverage rule, the input-shape coverage rule, the evaluable-case rule, the `seed_refs` map, the `correction_evidence` schema, or the optional `eligibility` block. Backward compatibility: `validate_dataset` accepts legacy datasets that omit the new blocks and continues to refuse the empty-catalog regression documented by Subphase 4.11.3 only when `commerce_catalog_inventory` is also absent.

## Impact

- `backend/services/product_recognition_calibration_runner.py` — replace the empty-catalog branch at `runner.py:636` and `runner.py:677` with a dispatch: when `source_case["catalog_scope"] == "commerce_dynamic_database"`, the runner resolves the cached fresh DB catalog for `source_case["id_comercio"]` (loading it on first use from PostgreSQL through `load_commerce_catalog_from_database(self._session, id_comercio)`) and passes the same catalog to both the observation and prediction steps; otherwise (the `in_memory` branch), keep the embedded catalog verbatim. The vector search branch at `runner.py:650-660` is unchanged; the boundary check uses `set(case["allowed_candidate_ids"])` as before. Add a deterministic `StaleCommerceCatalogError` refusal that fails closed when the freshly loaded DB catalog's fingerprint does not match the persisted `commerce_catalog_fingerprint[<id_comercio>]` (or when the persisted fingerprint is absent); the CLI returns non-zero and no report is emitted. The freshly loaded DB catalog — never the persisted inventory — is the catalog handed to the recognizer.
- `backend/services/product_recognition_calibration_commerce_catalog.py` — single source of the fresh-DB catalog loader `load_commerce_catalog_from_database(session, id_comercio) -> CommerceCatalog` that mirrors `backend/tests/manual_product_recognizer.py::_load_catalog` (joining `ProductoPresentacion` with `Producto` and `Presentacion`, filtering to `id_comercio == id_comercio`, returning the runtime-shaped entries with all four availability flags preserved). The function executes exactly one query per call. The runner MUST cache the result on `self._commerce_catalog_cache: dict[int, CommerceCatalog]` and MUST NOT issue more than one catalog query per commerce per calibration run.
- `backend/scripts/calibration_inventory.py` — add `--mode regenerate-commerce-catalog` (and `--commerce-id`) that loads every commerce-scoped `ProductoPresentacion` row for the given commerce (including rows whose `activo`, `producto_activo`, `presentacion_activo`, or `disponible` is `false`), builds the catalog entries (using the same field shape as `_load_catalog`, with all four flags preserved), persists them under `dataset["commerce_catalog_inventory"][str(id_comercio)]`, and writes the SHA-256 fingerprint under `dataset["commerce_catalog_fingerprint"][str(id_comercio)]`. The existing `_resolve_seed_refs`, `_validate_seed_refs`, `_regenerate`, and `--mode regenerate` are unchanged; the existing `seed_refs` map and `inventory_fingerprint` derivation are unchanged; `validate_dataset` continues to accept legacy datasets.
- `backend/services/product_recognition_calibration_policy.py::validate_dataset` — accept the optional `commerce_catalog_inventory` and `commerce_catalog_fingerprint` blocks on `schema_version: 3` datasets without rejecting legacy datasets that omit them and without bumping `schema_version`. The existing `seed_refs` validation, `correction_evidence` validation, and `inventory_fingerprint` derivation are unchanged.
- `backend/data/product_recognition_calibration_cases.json` — the dataset's `seed_refs`, `inventory_fingerprint`, the 11 preserved cases, the 36 expanded cases, the schema, and the eligibility block are unchanged; the new `commerce_catalog_inventory` and `commerce_catalog_fingerprint` blocks are added by the inventory regeneration step and committed under the change root.
- `backend/recognizers/product_recognizer.py` — not modified. The fuzzy recognizer continues to operate against the catalog passed by the runner; no score, threshold, alias, token, segmenter, or filter change.
- `backend/recognizers/fuzzy_product_recognizer.py` — not modified.
- `backend/cli/calibrate_product_recognizer.py` — not modified. The CLI continues to invoke the runner with the same flags; the diagnostic surface from Subphase 4.11.3 (`--diagnose`, `--diagnose-output`, `mismatch_category_counts`) is reused to evidence the before / after state.
- Tests: `backend/tests/test_product_recognition_calibration_4_11_4.py` gains regression tests proving no label leakage (the catalog handed to the recognizer is the freshly loaded DB catalog; the catalog is identical when `allowed_candidate_ids` change; the catalog is identical when `expected_producto_presentacion_id` changes; restricted candidates remain in the catalog and are flagged by the evaluator; entries from another commerce are absent; inactive and unavailable entries remain present with their original flags and the recognizer routes matching unavailable entries into `encontrados_no_disponibles` while available entries still appear in `disponibles`; no inactive entry is silently removed before recognition; commerce isolation is enforced; catalog contents remain independent from expected-case fields); a competing-product regression test pins that a plausible product outside `allowed_candidate_ids` is present in the fresh DB catalog and the recognizer can return it (the recognizer is not artificially constrained); a `StaleCommerceCatalogError` regression test mutates the database between two regenerations and asserts the runner fails closed with a deterministic error naming the offending `id_comercio` (the persisted inventory is the comparison anchor, not the runtime source). The Subphase 4.11 / 4.11.1 / 4.11.2 / 4.11.3 test suites must remain green.
- OpenSpec: delta specs are added to the change root under `openspec/changes/subphase-4-11-4-correct-real-fuzzy-product-recognition-failures/specs/<capability>/spec.md`; main specs are not modified until the user runs `/opsx:sync` after implementation.
- Runtime: no customer-facing behavior changes; fuzzy mode stays authoritative and the diagnostic mode stays opt-in. No claim is made that any specific pre-fix failure count will move to zero — only that the empty-catalog defect is eliminated and that residual failures are evidence-based and reclassified honestly under the Subphase 4.11.3 taxonomy.
