## Context

Subphase 4.11.3 archived at `openspec/changes/archive/2026-08-04-subphase-4-11-3-calibration-evaluation-mismatch/` and closed the dataset / seed / identifier defect surface. The diagnostic surface (`--diagnose`, per-case `mismatch_category`, `mismatch_category_counts`) is portable and the after-fix calibration report is committed alongside. The post-fix report shows:

- `real_fuzzy_recognizer_failure: 29` and `real_hybrid_recognizer_failure: 8` against `mismatch_category_counts.total = 37` (47 evaluated − 10 correct);
- the seven dataset / seed / identifier categories all at `0`;
- every fuzzy failure carries `catalog_scope: "commerce_dynamic_database"`.

What Subphase 4.11.3 proved and what it did not prove is the central question for 4.11.4. Subphase 4.11.3 proved that the evaluator (`_hybrid_prediction`, `_prediction`, `_strategy_metrics`, `_resolved_expected_id`) and the expected identifiers (`expected_producto_presentacion_id`, `allowed_candidate_ids`, `restricted_candidate_ids`, `expected_decision`, `expected_producto_presentacion_id_ref`) are valid: every `mismatch_category` not classified as `real_fuzzy_recognizer_failure` / `real_hybrid_recognizer_failure` / `correct` is at `0`, which means none of the seven dataset / seed / identifier defect categories fired. Subphase 4.11.3 did **not** prove that the runtime fuzzy recognizer itself fails for the 29 fuzzy cases — it proved only that the offline calibration environment is broken in a way that masks the recognizer's real behavior.

Inspection of `ProductRecognitionCalibrationRunner.run` (`backend/services/product_recognition_calibration_runner.py:600-700`) shows the broken environment: at `runner.py:636` the case dict is augmented with `catalog = dataset["catalogs"][source_case["catalog_fixture"]].get("entries", [])`. For `catalog_scope: "commerce_dynamic_database"` cases the dataset fixture is empty by design (Subphase 4.11.1 requirement), so the fuzzy recognizer at `runner.py:640` is invoked with `catalog = []`. `FuzzyProductRecognizer.recognize` delegates to `product_recognizer.detectar_productos` (`backend/recognizers/fuzzy_product_recognizer.py:7-16`), which calls `_extraer_candidatos` (`backend/recognizers/product_recognizer.py:402-498`) — that function returns `[]` against an empty catalog, so fuzzy decision becomes `unknown` regardless of whether the runtime would have matched the candidate. The vector search at `runner.py:650-660` is correctly given `allowed_candidate_ids` and finds candidates, which is why hybrid often finds the right `producto_presentacion.id` even though fuzzy misses it.

The runtime catalog assembly path is the reference for what the calibration environment must reproduce. Runtime call sites (`backend/intents/context/product_selection_context_resolver.py:165` and the matching code paths in `product_modification_resolver.py`, `quitar_producto_recognizer.py`, `modificar_producto_recognizer.py`, the test fixtures in `backend/tests/api_smoke.py`, and the manual loader at `backend/tests/manual_product_recognizer.py::_load_catalog` line 31) all hand `detectar_productos` a list of `producto_presentacion` dicts with the documented field shape (`producto_presentacion_id`, `producto_id`, `presentacion_id`, `categoria_id`, `producto_nombre`, `categoria_nombre`, `presentacion_codigo`, `presentacion_descripcion`, `activo`, `producto_activo`, `presentacion_activo`, `disponible`). `_preparar_catalogo` (`backend/recognizers/product_recognizer.py:244-262`) normalizes those dicts into the scoring catalog (`id`, `nombre_normalizado`, `nombre_fonetico`, `nombres_aliases_normalizados`, `producto_completo`). The recognizer's `disponibles` vs `encontrados_no_disponibles` split (`backend/recognizers/product_recognizer.py:543-561`) is the runtime active-filter: a product is classified unavailable if any of `producto_activo`, `presentacion_activo`, `activo`, `disponible` is false.

The 11 preserved `catalog_scope: "in_memory"` Subphase 4.11 cases use embedded `catalogs[*].entries` and work correctly — they must keep working unchanged. The current `seed_refs` map and the existing `inventory_fingerprint` at `runner.py:612-628` are part of the `schema_version: 3` contract and detect stale `seed_refs`; they do not detect stale commerce-catalog rows and are not a substitute for commerce-catalog fingerprinting.

This change corrects the calibration environment only. It does not promote any pre-fix failure count to zero — it eliminates the empty-catalog defect, eliminates label leakage, and surfaces the recognizer's real behavior. Cases that still fail after the fix are evidence-based residual failures and are reclassified honestly under the Subphase 4.11.3 taxonomy.

## Goals / Non-Goals

**Goals:**

- Reconstruct the offline calibration environment so that the fuzzy recognizer receives a faithful full runtime-compatible commerce catalog for every `commerce_dynamic_database` case — every commerce-scoped `producto_presentacion` entry returned by the real runtime catalog assembly, including entries whose availability flags are `false`, matching the runtime call sites' catalog assembly byte-for-byte.
- Guarantee that no expected-case label (`allowed_candidate_ids`, `restricted_candidate_ids`, `expected_decision`, `expected_producto_presentacion_id`, `expected_producto_presentacion_id_ref`, or any other expectation) influences catalog construction. The catalog is determined solely by `id_comercio` and the current database.
- Guarantee that `allowed_candidate_ids` and `restricted_candidate_ids` are applied strictly in the evaluator, after recognition, exactly as the Subphase 4.11 / 4.11.1 / 4.11.3 boundary contract documents.
- Guarantee that the calibration issues exactly one catalog query per commerce per calibration run (loading the fresh runtime-compatible catalog from PostgreSQL on first use and caching it on `self._commerce_catalog_cache` for the duration of the run). The persisted `commerce_catalog_inventory` block (when present) and its `commerce_catalog_fingerprint` are reproducible evidence of the database snapshot the change was authored against; they are NOT the runtime source of truth and the runner MUST NOT hand the persisted inventory to the recognizer.
- Preserve every existing Subphase 4.11 / 4.11.1 / 4.11.2 / 4.11.3 invariant: fuzzy mode authoritative, `PRODUCT_RECOGNIZER_MODE` untouched, no embedding model / Ollama / vector / latency-budget / threshold / weight change, the 11 preserved cases byte-identical, the dataset `schema_version` and eligibility block stable, the diagnostic mode opt-in, the existing JSON report schema stable modulo documented new fields, the inventory fingerprint stable, the seed_refs map format stable, the `correction_evidence` schema stable.
- Reuse the Subphase 4.11.3 diagnostic surface (`mismatch_category`, `mismatch_category_counts`, `--diagnose`, `--diagnose-output`) to evidence the before / after state.

**Non-Goals:**

- Modifying `product_recognizer.detectar_productos`, `_extraer_candidatos`, `_calcular_score`, `_extraer_presentacion`, `_filtrar_por_tokens_clave`, `_preparar_catalogo`, `PRESENTACION_ALIASES`, fuzzy scores, fuzzy thresholds, fuzzy ranking, fuzzy output shape, the `disponibles` / `encontrados_no_disponibles` split, or any other recognizer helper.
- Activating hybrid runtime (`PRODUCT_RECOGNIZER_MODE != "fuzzy"`), changing the embedding model, changing vector dimensions, or rebuilding vector data.
- Bumping `schema_version`, deleting or weakening any of the 11 preserved Subphase 4.11 cases, changing the 11 + 36 case count, raising the `required_improvement` or `false_positive_tolerance` thresholds, or changing the latency budget.
- Generalising the commerce catalog loader beyond the calibration runner; the runtime fuzzy recognizer continues to operate on the in-memory catalog passed by its caller (handler / resolver / call site) and is not coupled to the calibration inventory.
- Introducing a runtime dependency on `seed_refs`, `inventory_fingerprint`, `commerce_catalog_inventory`, or any other calibration artefact.
- Promising that any specific pre-fix failure count (29 fuzzy, 8 hybrid, or any other) will move to zero. Residual failures after the fix are evidence-based and are reclassified under the Subphase 4.11.3 taxonomy; they become the documented remaining work for a future subphase only if the recognizer's behavior is shown to be defective on a faithful full-commerce catalog.

## Decisions

**Decision 1 — The fuzzy catalog is built from the full runtime-compatible commerce catalog, not from `allowed_candidate_ids` and not from an "active-only" subset.**

Rationale: the runtime recognizer receives the full commerce catalog; restricting the catalog to `allowed_candidate_ids` would narrow the recognizer's search space to expected-case information and inflate calibration accuracy. The calibration environment must mirror the runtime environment so that the calibration measures what the runtime sees. Alternatives considered: (a) build the catalog from `seed_refs_inventory` rows (the original 4.11.4 proposal) — rejected because it leaks expected-case information into candidate generation; (b) build the catalog from a randomly-sampled subset of the commerce — rejected because sampling is not what the runtime does and would invalidate the comparison.

**Decision 2 — `allowed_candidate_ids` and `restricted_candidate_ids` are applied in the evaluator, never in catalog construction.**

Rationale: the Subphase 4.11 calibration spec already documents the evaluator boundary contract (`allowed_candidate_ids` for top-1 correctness, `restricted_candidate_ids` for non-regression). Applying them in the evaluator preserves the Subphase 4.11 / 4.11.1 / 4.11.3 invariants; applying them at catalog construction would silently constrain the recognizer and inflate accuracy. Alternatives considered: (a) keep restricted candidates out of the catalog (the original 4.11.4 proposal) — rejected because it lets the recognizer never see a candidate it should be flagged for rejecting; (b) keep allowed candidates only (the original 4.11.4 proposal) — rejected for the same reason with stronger label-leakage consequences.

**Decision 3 — Per-commerce catalog is loaded fresh from PostgreSQL once per calibration run and cached on `self`.**

Rationale: the fresh DB catalog is the runtime source of truth. Comparing the persisted inventory against itself would not detect real database changes, so the runner MUST load the catalog from PostgreSQL through `load_commerce_catalog_from_database(self._session, id_comercio)` on first reference, cache it on `self._commerce_catalog_cache`, and reuse the cached list for every case at that commerce. The persisted `commerce_catalog_inventory` block (when present) is reproducible evidence of the database snapshot the change was authored against, never the runtime source. Alternatives considered: (a) load from persisted inventory — rejected because it cannot detect real database drift; (b) one query per case — rejected as prohibitively slow and as introducing per-case timing variance that would distort the latency-p95 metric; (c) shared global module-level cache — rejected because calibration runs are short-lived processes and module-level state complicates testing.

**Decision 4 — `commerce_catalog_inventory` and `commerce_catalog_fingerprint` are reproducible evidence; the runner compares the fresh DB catalog's fingerprint against the persisted `commerce_catalog_fingerprint` to detect drift.**

Rationale: persisting `commerce_catalog_inventory` and `commerce_catalog_fingerprint` makes the calibration reproducible and traceable to a specific database snapshot — these are evidence, not the runtime source. At calibration time, the runner loads the fresh DB catalog for each commerce it visits, computes its SHA-256 fingerprint (sorted object keys, stable list order, finite JSON values), and compares it against `dataset["commerce_catalog_fingerprint"][str(id_comercio)]`. On mismatch the runner raises `StaleCommerceCatalogError` (CLI returns non-zero, no report emitted) naming the offending `id_comercio` and the expected / actual fingerprints. The two fingerprint blocks do not overlap: `inventory_fingerprint` covers `seed_refs` only; `commerce_catalog_fingerprint[<id_comercio>]` covers the full commerce catalog snapshot the change was authored against. The existing `inventory_fingerprint` derivation at `runner.py:612-628` and the existing stale-`seed_refs` guard are preserved unchanged. Alternatives considered: (a) compare the persisted catalog against itself — rejected because it cannot detect real database drift; (b) merge the two fingerprints into one — rejected because it conflates two independent staleness signals and makes diagnosis harder; (c) rely solely on `seed_refs` for staleness — rejected because `seed_refs` does not cover the full commerce catalog and would silently allow stale rows to leak into the runner.

**Decision 5 — Inventory regeneration adds a new `--mode regenerate-commerce-catalog --commerce-id <id>` subcommand without changing `--mode regenerate`.**

Rationale: `--mode regenerate` is the documented Subphase 4.11.1 / 4.11.3 entry point for `seed_refs` and continues to be the single source of truth for the `seed_refs` map and `inventory_fingerprint`. The new subcommand handles the full commerce catalog independently and can be run after `--mode regenerate` (or in a single invocation that calls both helpers). The existing `_resolve_seed_refs` and `_validate_seed_refs` are unchanged. Alternatives considered: (a) extend `--mode regenerate` to also produce the commerce catalog — rejected because it conflates two independent inventory concerns; (b) write the commerce catalog into a sidecar JSON file — rejected because it introduces a second portable reference surface.

**Decision 6 — The catalog loader follows the existing runtime field shape (every documented field), sorted by `producto_presentacion_id` ascending, deterministic across runs.**

Rationale: the runtime field shape is the contract `_preparar_catalogo` consumes; mirroring it guarantees byte-identical normalized output for the same input. Sorting by primary key and deduping by `producto_presentacion_id` makes re-runs byte-identical for equal database state. Alternatives considered: (a) load only the fields `_preparar_catalogo` reads — rejected because the runtime `disponibles` / `encontrados_no_disponibles` split reads the active flags and we want to keep the recognizer's behavior unchanged for inactive products; (b) load on demand with pagination — rejected as unnecessary complexity for ~50–200 rows per commerce.

**Decision 7 — Test surface mirrors Subphase 4.11.3's regression file `test_product_recognition_calibration_4_11_3.py` and adds the no-label-leakage regressions required by this change.**

Rationale: regression file `backend/tests/test_product_recognition_calibration_4_11_4.py` covers: (a) the runner loads the fresh DB catalog for every `commerce_dynamic_database` case at the case's `id_comercio` and the catalog is identical across cases at the same commerce; (b) the catalog is the fresh DB catalog — never the persisted inventory — even when the dataset's `commerce_catalog_inventory` is present and matches; (c) the catalog is unchanged when `allowed_candidate_ids` change; (d) the catalog is unchanged when `expected_producto_presentacion_id` change; (e) restricted candidates are present in the fresh DB catalog and the evaluator flags them when returned by the recognizer; (f) entries from another commerce are absent; (g) inactive and unavailable entries remain present in the fresh DB catalog with their original flags (`activo`, `producto_activo`, `presentacion_activo`, `disponible` preserved exactly) and the recognizer routes matching unavailable entries into `encontrados_no_disponibles` while available entries still appear in `disponibles`; (h) catalog construction is deterministic (sorted, deduped, byte-identical re-runs); (i) the fresh DB catalog is loaded exactly once per commerce per calibration run (no per-case database query, no per-call database query); (j) the 11 preserved `in_memory` cases are unchanged; (k) no new CLI flag or runtime recognizer behavior is introduced; (l) a competing-product regression pins that a plausible product outside `allowed_candidate_ids` is present in the fresh DB catalog and the recognizer can return it (the recognizer is not artificially constrained); (m) the `StaleCommerceCatalogError` refusal fails closed when the fresh DB catalog fingerprint does not match the persisted `commerce_catalog_fingerprint[<id_comercio>]`, naming the offending `id_comercio` and the expected / actual fingerprints; (n) the existing `seed_refs` / `inventory_fingerprint` stale guard is unchanged and still triggers independently. The Subphase 4.11 / 4.11.1 / 4.11.2 / 4.11.3 regression suites remain green.

## Risks / Trade-offs

- [Risk] The full-commerce catalog could let the fuzzy recognizer emit candidates the evaluator rejects, increasing false positives → Mitigation: this is the documented honest behavior. The calibration metrics now measure the recognizer's real precision / recall against the full catalog; the post-fix metrics are the substrate for any future Subphase 4.12 eligibility decision. The Subphase 4.11.3 `mismatch_category_counts` aggregate honestly records the new failure distribution.
- [Risk] Confusion between catalog assembly and availability filtering → Mitigation: catalog assembly is strictly the same path as `backend/tests/manual_product_recognizer.py::_load_catalog` — every commerce-scoped `producto_presentacion` row is loaded from PostgreSQL with its four runtime availability flags preserved verbatim. Availability filtering is the recognizer's job, performed by the existing `disponibles` / `encontrados_no_disponibles` split (`backend/recognizers/product_recognizer.py:543-561`). A regression test pins that inactive entries are present in the fresh DB catalog and the recognizer routes them under `encontrados_no_disponibles`.
- [Risk] The persisted `commerce_catalog_inventory` could drift from the live database and silently mask real catalog changes → Mitigation: the persisted inventory is reproducible evidence only; the runner loads the fresh DB catalog at calibration time and computes its fingerprint; the `StaleCommerceCatalogError` refusal fails closed when the fresh DB fingerprint does not match the persisted `commerce_catalog_fingerprint[<id_comercio>]`. The persisted inventory is never handed to the recognizer.
- [Risk] Tests could mask label leakage if they only assert the catalog size → Mitigation: every no-label-leakage regression asserts the catalog identity under three perturbations (changed `allowed_candidate_ids`, changed `expected_producto_presentacion_id`, swapped `id_comercio`) and asserts that a competing product outside `allowed_candidate_ids` is present in the catalog and the recognizer can return it.
- [Risk] The fresh-DB catalog loader could introduce variable latency that distorts the latency-p95 metric → Mitigation: the loader runs once per commerce and the result is cached on `self._commerce_catalog_cache` for the duration of the run, so per-case timing is unaffected. The Subphase 4.11 latency gate still applies; the loader cost is added to the per-run startup cost, not the per-case hot path.
- [Risk] The fix could be read as activating hybrid runtime or as a production recognizer change → Mitigation: `PRODUCT_RECOGNIZER_MODE` is not touched, no recognizer is replaced, no recognizer factory is changed, no recognizer mode setting is added, no observability field is added, no customer-facing call site is changed; the change is documented as confined to the offline calibration pipeline.
- [Trade-off] Increased dataset size (~50 KB per commerce in `commerce_catalog_inventory`) — accepted; the persisted block is reproducible evidence only and the runner does not depend on it for correctness. The dataset remains small.
- [Trade-off] Honest post-fix metrics may not move the eligibility verdict from `not_eligible` to `eligible` — accepted; the goal of 4.11.4 is to surface the recognizer's real behavior, not to flip the verdict. Residual failures become the documented future work for a future subphase.

## Migration Plan

1. Inspect the runtime catalog assembly path (the existing `_load_catalog` helper, the resolver / recognizer call sites, the `disponibles` / `encontrados_no_disponibles` split) and pin the documented field shape in the spec delta for `expand-product-recognition-calibration-dataset-4-11-1`.
2. Implement the fresh-DB catalog loader `load_commerce_catalog_from_database(session, id_comercio) -> CommerceCatalog` in `backend/services/product_recognition_calibration_commerce_catalog.py`. The loader mirrors `backend/tests/manual_product_recognizer.py::_load_catalog` (joining `ProductoPresentacion` with `Producto` and `Presentacion`, filtering to `id_comercio == id_comercio`) and preserves all four runtime availability flags verbatim. The loader executes exactly one query per call; the runner caches the result on `self._commerce_catalog_cache` and never queries more than once per commerce per run.
3. Implement `fingerprint_commerce_catalog(catalog) -> str` (SHA-256 of canonical JSON per commerce) and the runner's `StaleCommerceCatalogError` refusal: at first reference to each commerce, the runner loads the fresh DB catalog, computes its fingerprint, compares it against `dataset["commerce_catalog_fingerprint"][str(id_comercio)]`, and fails closed with `StaleCommerceCatalogError` on mismatch (or when the persisted fingerprint is absent). The existing `seed_refs` / `inventory_fingerprint` guard is unchanged.
4. Add `backend/scripts/calibration_inventory.py --mode regenerate-commerce-catalog --commerce-id <id>` that loads the per-commerce catalog through `load_commerce_catalog_from_database`, persists it under `dataset["commerce_catalog_inventory"][str(id_comercio)]`, computes the fingerprint through `fingerprint_commerce_catalog`, and persists it under `dataset["commerce_catalog_fingerprint"][str(id_comercio)]`. The persisted blocks are reproducible evidence of the database snapshot the change was authored against; the runner does not use them as the runtime source. Commit the regenerated dataset under the change root.
5. Patch `ProductRecognitionCalibrationRunner.run` to load the fresh DB catalog once per commerce (cached on `self._commerce_catalog_cache`), pass it to every `commerce_dynamic_database` case, and preserve the embedded-catalog path for `in_memory` cases. The vector search branch at `runner.py:650-660` is unchanged. Apply `allowed_candidate_ids` / `restricted_candidate_ids` strictly in the evaluator.
6. Update `validate_dataset` to accept the new optional blocks on `schema_version: 3` datasets without rejecting legacy datasets.
7. Add `backend/tests/test_product_recognition_calibration_4_11_4.py` with the no-label-leakage, per-commerce-caching, in-memory-unchanged, fresh-DB-fingerprint-refusal, and competing-product regressions. The fresh-DB-fingerprint refusal regression mutates the database between two regenerations and asserts the runner fails closed with a deterministic error naming the offending `id_comercio`.
8. Re-run the documented calibration command and reclassify every case under the Subphase 4.11.3 taxonomy. Record the post-fix `mismatch_category_counts` aggregate honestly; do not promise that any specific pre-fix count will move to zero.
9. Rollback: revert the runner dispatch and the loader; the catalog loader, the fingerprint refusal, and the new tests can be left in place as harmless dead code, or removed in the same revert.
