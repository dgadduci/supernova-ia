## Context

`PendingIntents` already models one active intent plus a FIFO queue, and the pending-intent service already supports `enqueue` and `remove_active`. The runtime does not use those operations for a classifier result containing multiple additions: each pending `process_initial_agregar_producto` call invokes `set_pending_intent`, overwriting `active`; ready initial results are returned but not handled; and pending dispatch/execution returns one result and clears the entire state after a definitive outcome. The correction spans orchestration boundaries but must retain the current handler, persistence, and outer transaction ownership.

## Goals / Non-Goals

**Goals:**

- Preserve all `agregar_producto` items from one classification in classifier order.
- Keep exactly one unresolved item active and store later additions in the existing FIFO queue.
- Execute consecutive ready additions without another user message, pause at the next unresolved addition, and resume from that item on the next product-selection reply.
- Return all outcomes generated by one incoming message in execution order.
- Clear pending context only when no queued addition remains.

**Non-Goals:**

- Changing product recognition, matching, quantities, pricing, consolidation, or customer-response wording.
- Generalizing batching to `quitar_producto` or `modificar_producto`.
- Changing `PendingIntents`, database models, migrations, HTTP schemas, transaction ownership, or queue persistence format.
- Adding retries, async processing, commits, or rollbacks below the transactional processor.

## Decisions

### Centralize batch preservation in the initial dispatcher

The initial dispatcher will collect `agregar_producto` results in classifier order and establish pending state deliberately: the first unresolved addition becomes active and every later addition that must survive is appended through `enqueue`. This prevents repeated orchestration-level `set_active` calls from replacing earlier work. The `agregar_producto` initial orchestrator remains responsible for recognition and typed intent construction, but pending placement must respect pre-existing active state rather than overwrite it.

Alternative: change `set_pending_intent` globally to enqueue whenever active is occupied. Rejected because that helper is shared by distinct context types; silently mixing incompatible contexts would broaden behavior beyond this defect.

### Use FIFO promotion as the sole queue transition

After a definitive active result, execution removes only that active item through `remove_active`, which promotes the queue head. It never calls `clear_pending_context` while another item exists. Classifier order is therefore the execution order without introducing indexes or a second batch model.

Alternative: copy and rewrite the entire pending payload in each orchestrator. Rejected because existing service operations already encode and test FIFO persistence.

### Drain consecutive ready agregar_producto items synchronously

Pending-context execution will return `list[ProcessedIntent]`. It executes the active ready addition, records the result, promotes the queue after `executed` or definitive `rejected`, and repeats while the promoted active item is ready. It stops when the next active item is `pending_resolution` or `failed`; when no active item remains it clears `context_type`.

Alternative: execute at most one queued item per later customer message. Rejected because it would require unrelated input to finish already-resolved additions and would leave the batch artificially stuck.

### Propagate lists through pending dispatch and incoming orchestration

`dispatch_pending_context` returns a list for every path, wrapping a single unresolved/rejected result when no draining occurs. `process_incoming_message` forwards that list unchanged, matching its existing public return type and allowing the response orchestrator to build one response per result without API schema changes.

Alternative: keep scalar pending dispatch and discard intermediate executed results. Rejected because every preserved addition needs a customer-visible outcome and deterministic ordering.

### Preserve failure and transaction semantics

A `failed` result remains active with its queue intact and stops draining. Raised exceptions propagate unchanged. No changed orchestration layer commits or rolls back; `process_incoming_message_transactional` still performs exactly one outer commit on success or one rollback on exception.

## Risks / Trade-offs

- [Mixed intent types could be accidentally queued behind product selection] → Limit the new queueing/draining behavior to `handler == "agregar_producto"` and preserve existing behavior for other handlers.
- [A handler failure after earlier additions executed in memory could expose partial state] → Stop on returned `failed`; let raised exceptions reach the transactional wrapper so its rollback remains authoritative.
- [Changing pending dispatcher from scalar to list can break direct callers] → Update all call sites and focused tests together; the top-level incoming orchestrator already returns a list.
- [Rejected queued additions could block later valid additions] → Treat definitive `rejected` like `executed` for promotion, retain the rejected outcome, and continue draining.
- [Repeated resolver ambiguity could reorder the queue] → Update only `active`; leave `queue` byte-for-byte/order equivalent until promotion.

## Migration Plan

No data migration is required because persisted `PendingIntents` already contains `active` and `queue`. Deploy code and tests together. Existing sessions with an active item and queue are consumed using the corrected FIFO behavior. Rollback consists of reverting the orchestration changes; the stored payload remains compatible with the prior schema.
