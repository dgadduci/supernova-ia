## Context

Subphases 3.24 → 3.28 produced a complete modern intents pipeline:

- `backend/intents/orchestration/incoming_message_orchestrator.py` (`process_incoming_message`, Subphase 3.24) — message validation + routing between `dispatch_pending_context` and `dispatch_initial_message`.
- `backend/intents/orchestration/initial_intent_dispatcher.py` (`dispatch_initial_message`, Subphase 3.23) and `pending_context_dispatcher.py` (`dispatch_pending_context`, Subphase 3.18) — the two routing targets.
- `backend/intents/orchestration/transactional_message_processor.py` (`process_incoming_message_transactional`, Subphase 3.26) — owns the single `commit()` / `rollback()` boundary.
- `backend/intents/orchestration/incoming_message_response_orchestrator.py` (`process_incoming_message_with_responses`, Subphase 3.28) — converts each `ProcessedIntent` into a `CustomerResponse` (delegating `agregar_producto` to `build_agregar_producto_response`, generic fallback for everything else).
- `backend/intents/schemas/customer_response.py` (`CustomerResponse`, Subphase 3.27) — Pydantic schema with `message`, `intent`, `status` strings.
- Integration coverage (`backend/tests/test_incoming_message_integration.py`, Subphase 3.25) — proves both routing branches against `supernova_test`.

What is still missing: a local HTTP seam that exposes the modern pipeline to a caller running `uvicorn backend.main:app`. The existing routers (`backend/routers/sessions.py`, `backend/routers/comercios.py`, `backend/routers/producto_queries.py`, etc.) are CRUD wrappers around services and repositories — none of them reaches into the intents package. Future adapters (Twilio webhook, queue worker, integration test harness) would have to import the orchestrator directly, hand-roll a SQLAlchemy session, and shape JSON themselves. That duplicates the wrapper that the transactional processor / response orchestrator pair was designed to own.

Subphase 3.29 closes that gap by adding a single FastAPI router (`backend/routers/incoming_messages.py`) with one endpoint (`POST /comercios/{comercio_id}/clientes/{cliente_id}/incoming-messages`) that:

1. Validates the inbound JSON body (`IncomingMessageRequest`).
2. Resolves the active conversation through the existing `SessionService.get_active(comercio_id, cliente_id)`.
3. Delegates to `process_incoming_message_with_responses(db, session, message)` exactly once.
4. Wraps the resulting `list[CustomerResponse]` in `IncomingMessageResponse`.
5. Translates the existing exceptions (`SessionNotFound`, `TypeError`, `ValueError`) into the corresponding `HTTPException`; lets everything else propagate unchanged so FastAPI's default handler turns it into 500 without swallowing context.

The router is wired in `backend/main.py` next to `sessions.router`. The router module, the schemas module, and the existing response orchestrator are the only files touched; nothing in `backend/intents/*`, `backend/services/*`, `backend/repositories/*`, `backend/models/*`, `backend/llm/*`, or any other router changes. Tests live in a new `backend/tests/test_incoming_messages_endpoint.py` that drives the endpoint via `fastapi.testclient.TestClient` with `SessionService.get_active` and `process_incoming_message_with_responses` patched at the router's import site — mirroring the style of `backend/tests/test_incoming_message_response_orchestrator.py` and `backend/tests/test_transactional_message_processor.py`.

## Goals / Non-Goals

**Goals:**

- Expose `POST /comercios/{comercio_id}/clientes/{cliente_id}/incoming-messages` as the single local HTTP entry point to the modern intents pipeline.
- Add `IncomingMessageRequest` (`message: str`) and `IncomingMessageResponse` (`responses: list[CustomerResponse]`) Pydantic schemas that act as the local HTTP contract.
- Resolve the active conversation through `SessionService.get_active(comercio_id, cliente_id)`; do not introduce a new repository query.
- Delegate to `process_incoming_message_with_responses(db, session, message)` exactly once per request and return its `list[CustomerResponse]` wrapped in `IncomingMessageResponse`.
- Translate `SessionNotFound` → `HTTPException(404, detail=str(exc))`, `TypeError` → `HTTPException(400, detail=str(exc))`, `ValueError` → `HTTPException(400, detail=str(exc))`; do not catch, wrap, or translate any other exception — let FastAPI's default handler turn it into 500.
- Keep the router free of LLM calls, direct SQLAlchemy access, repository imports, transaction management (`db.commit` / `db.rollback` / `db.flush` / `db.refresh` / `db.expire` / `db.begin`), mutation outside the modern pipeline, Twilio integration, queue promotion, retry / backoff, async wrappers, logging, response beautification, locale selection, template engines, and imports from `backend/old_project/`.
- Add focused tests in `backend/tests/test_incoming_messages_endpoint.py` that mock `SessionService.get_active` and `process_incoming_message_with_responses` at the router's import site and assert the happy path, the `agregar_producto` and unsupported-intent branches, the `SessionNotFound` → 404 translation, the `TypeError` / `ValueError` → 400 translation, and the `__all__` discipline on the router and schemas modules.

**Non-Goals:**

- Adding a webhook adapter for Twilio (or any external transport) — that belongs to a future subphase that consumes the same `process_incoming_message_with_responses`.
- Adding authentication, authorization, rate limiting, request signing, or any other HTTP middleware.
- Adding a queue / background task that re-routes the inbound message; the endpoint is synchronous and returns the response inline.
- Modifying `process_incoming_message`, `process_incoming_message_transactional`, `process_incoming_message_with_responses`, `dispatch_initial_message`, `dispatch_pending_context`, `process_initial_agregar_producto`, `IntentClassifier`, `QueryLlm`, `build_agregar_producto_response`, the response orchestrator module, the transactional processor module, the orchestrator module, any recognizer, resolver, processor, handler, service, repository, model, migration, configuration, FastAPI dependency, or any other router.
- Implementing session creation, session lookup by id, pedido association, or session closing through this endpoint; those live in `backend/routers/sessions.py` and are out of scope.
- Returning anything other than the `IncomingMessageResponse` envelope (no TwiML, no JSON-LD, no streaming responses, no `text/event-stream`, no websocket upgrades).
- Adding OpenAPI examples, response descriptions, or `responses=` decorators beyond the minimum needed for the schema to validate.
- Re-testing `process_incoming_message`, the transactional processor, the response orchestrator, the customer-response builder, the recognizer, the resolver, the processor, the handler, the dispatchers, or any other component already covered by their own unit / integration suites.

## Decisions

- **File location: `backend/routers/incoming_messages.py`.** Sits next to `backend/routers/sessions.py`, `backend/routers/comercios.py`, `backend/routers/producto_queries.py`, and the other routers. The `backend/routers/` package is the project's home for FastAPI route handlers; no new directory is introduced.
- **Schemas location: `backend/schemas/incoming_message.py`.** The `backend/schemas/` package already holds request / response Pydantic models (`backend/schemas/session.py`, `backend/schemas/pedido.py`, etc.); the new module follows the same `model_config = ConfigDict(extra="forbid")` discipline for the request model and `from_attributes=True` discipline for the response model. No new schema package is introduced.
- **Single endpoint: `POST /comercios/{comercio_id}/clientes/{cliente_id}/incoming-messages`.** Mirrors the existing `GET /comercios/{comercio_id}/clientes/{cliente_id}/activa` style for finding the active session, and is consistent with the `comercio_id` / `cliente_id` pair used by `SessionService.get_active`. Rationale: requiring a `session_id` would couple the endpoint to the URL of a session that already lives at `/sessions/{session_id}` and would force the caller to know the session id before sending a message. Using the comercio / cliente pair keeps the endpoint useful for any caller (Twilio webhook, test harness, queue worker) that only knows the customer and the merchant.
- **Single delegation to `process_incoming_message_with_responses`.** The endpoint calls the response orchestrator exactly once with `(db, session, message)`. Rationale: the response orchestrator already owns the inner transactional wrapper, the commit / rollback boundary, the per-intent dispatch, and the generic fallback; the router's job is to translate the HTTP layer into a single function call and back. Re-validating the message, re-routing on `session.context_type`, or invoking the transactional processor directly would bypass the response orchestrator's per-intent routing rule.
- **Active session lookup via `SessionService.get_active`.** The endpoint calls `service.get_active(comercio_id, cliente_id)` (the same method `GET /sessions/comercios/{comercio_id}/clientes/{cliente_id}/activa` already relies on). Rationale: the lookup logic, the FK ordering, and the `SessionNotFound` semantics already live in `SessionService`; a duplicate query in the new router would risk drift. `SessionNotFound` propagates from the service into the router where the translation to `HTTPException(404)` happens.
- **Three deterministic exception translations; everything else propagates.** The router catches exactly three exception types: `SessionNotFound` → `HTTPException(404, detail=str(exc))`, `TypeError` → `HTTPException(400, detail=str(exc))`, `ValueError` → `HTTPException(400, detail=str(exc))`. Any other exception (e.g., `QueryLlmError`, `pydantic.ValidationError`, `IntegrityError`, `RuntimeError`) propagates unchanged so FastAPI's default handler turns it into 500 without the router swallowing context. Rationale: a narrow `try/except` keeps the success path linear and the failure path linear; catching `Exception` would mask integration defects by returning 500 with a custom message that hides the original traceback.
- **`IncomingMessageRequest` enforces `message: str` with `extra="forbid"`.** Pydantic's built-in validation already rejects `None`, integers, and missing fields with a 422 response that FastAPI generates automatically; the `extra="forbid"` discipline keeps the request body tight. Rationale: the inner pipeline also validates (and raises `TypeError` for non-`str`, `ValueError` for empty / whitespace), but having the schema reject the obvious cases at the boundary keeps the documented 400 / 422 mapping simple and lets the router catch only the messages that survive the schema (e.g., empty strings, which Pydantic considers valid `str`).
- **`IncomingMessageResponse` wraps `responses: list[CustomerResponse]` rather than returning a bare list.** Rationale: a bare-list response is ambiguous (the inner list could be confused with a future envelope), and a wrapping object leaves room for future metadata (e.g., `session_id`, `comercio_id`, `timestamp`) without breaking callers. The wrapper costs nothing today and prevents churn tomorrow.
- **No logging in the router.** The modern pipeline already logs its own events through the dispatchers and the transactional processor; adding a fourth logging layer in the router would duplicate events. If a future audit trail is needed, it can wrap the router from outside.
- **No retry / backoff.** If `process_incoming_message_with_responses` raises, the router translates or propagates; it never retries the call. Rationale: any retry policy belongs to the future Twilio / queue adapters that own their idempotency story; the local HTTP endpoint is the simplest possible seam so any future policy can wrap it without undoing its work.
- **`__all__` discipline on the router and schemas modules.** The router exports only `router` through `__all__`; the schemas module exports only `IncomingMessageRequest` and `IncomingMessageResponse` through `__all__`. Rationale: matches the discipline used by every other router and schema module in the project and gives the test suite a single, stable handle to assert against.
- **Tests use `fastapi.testclient.TestClient`.** Same pattern as `backend/tests/api_smoke.py`; tests build a fresh `FastAPI()` app instance, mount the router directly with `app.include_router(router)`, override `get_session` with a `MagicMock(name="DatabaseSession")`, and patch `SessionService.get_active` and `process_incoming_message_with_responses` at the router's import site (`backend.routers.incoming_messages.SessionService` and `backend.routers.incoming_messages.process_incoming_message_with_responses`) using `unittest.mock.patch.object`. Rationale: building a fresh `FastAPI()` instance avoids mutating `backend.main.app` from the test module, and patching at the router's import site catches accidental re-imports through `backend.intents.orchestration.incoming_message_response_orchestrator` (the test should never reach there).
- **No live `supernova_test` connection in the new tests.** The endpoint is the seam between FastAPI and the modern pipeline; the modern pipeline is already integration-tested in `backend/tests/test_incoming_message_integration.py`. The endpoint tests only need to prove the HTTP translation, the schema validation, the exception mapping, and the delegation; they do not need a real database. Rationale: keeps the test fast and deterministic; integration coverage already exists for the pipeline itself.

## Risks / Trade-offs

- [Risk] The endpoint requires an active session for the given comercio / cliente pair; a missing session is 404, which is the correct semantic but may surprise callers expecting 400 → Mitigation: the spec explicitly states `SessionNotFound` → 404, the test suite covers that case, and the OpenAPI schema documents the 404 response (via FastAPI's automatic generation). A future caller can resolve the customer / session mismatch upstream.

- [Risk] The endpoint translates `TypeError` and `ValueError` from the pipeline to 400, but Pydantic's own validation (non-`str` `message`, missing `message`, extra fields) returns 422 by default → Mitigation: the spec explicitly maps the two layers (Pydantic 422, pipeline 400), the test suite covers both, and the OpenAPI schema documents both response codes. The asymmetry is documented and intentional.

- [Risk] The endpoint runs `process_incoming_message_with_responses` synchronously inside the request, including a potential LLM call; long-running requests could tie up a worker → Mitigation: the endpoint is the local seam, not the production webhook; future subphases that consume this seam (Twilio adapter, queue worker) will own the timeout, retry, and async strategy. The endpoint intentionally does not introduce async wrappers, retry, or queue promotion here.

- [Risk] Adding a new router increases the import surface and the risk of importing from `backend/old_project/` by accident → Mitigation: the test suite reads the router source from disk and asserts it does not contain `"from backend.old_project"`, `"import requests"`, `"import twilio"`, `"import asyncio"`, `"async def"`, `"logger."`, `"logging."`, `"print("`, `"time.sleep"`, `"retry"`, `"backoff"`, `"HTTPException"` outside the documented exception translations, or `"MessagingResponse"`. The router's `__all__` is asserted equal to `["router"]`.

- [Risk] The endpoint could be misused as a synchronous public webhook → Mitigation: the spec explicitly states that this is a local seam and that future adapters (Twilio, queue, etc.) will own transport concerns; the implementation does not add authentication, request signing, or rate limiting, which the project rule "do not anticipate future requirements" forbids.

- [Risk] `IncomingMessageResponse` wrapping `responses` adds a layer of indirection that costs a key in the JSON payload → Mitigation: the schema is a single Pydantic model with one field; the cost is negligible, and the envelope prevents future breaking changes (e.g., adding `session_id` or `timestamp` metadata).

## Migration Plan

1. Add `backend/schemas/incoming_message.py` exporting `IncomingMessageRequest` (`message: str` with `extra="forbid"`) and `IncomingMessageResponse` (`responses: list[CustomerResponse]` with `from_attributes=True`); no other module imports them yet.
2. Add `backend/routers/incoming_messages.py` exposing the single `POST /comercios/{comercio_id}/clientes/{cliente_id}/incoming-messages` route. The handler:
   - Takes `(comercio_id: int, cliente_id: int, payload: IncomingMessageRequest, service: SessionService = Depends(_service), db: Session = Depends(get_session))` from FastAPI's dependency injection.
   - Calls `session = service.get_active(comercio_id, cliente_id)`; on `SessionNotFound` raises `HTTPException(404, detail=str(exc)) from exc`.
   - Calls `responses = process_incoming_message_with_responses(db, session, payload.message)`; on `TypeError` / `ValueError` raises `HTTPException(400, detail=str(exc)) from exc`; any other exception propagates unchanged.
   - Returns `IncomingMessageResponse(responses=responses)`.
3. Wire the router in `backend/main.py` by adding `from backend.routers import (..., incoming_messages)` and `app.include_router(incoming_messages.router)` next to the existing `app.include_router(sessions.router)` line.
