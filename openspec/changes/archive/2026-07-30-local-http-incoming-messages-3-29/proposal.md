## Why

The modern intents pipeline (Subphases 3.24 → 3.28) ends with `process_incoming_message_with_responses(db, session, message) -> list[CustomerResponse]`, but nothing in `backend/routers/` exposes that seam to a local HTTP caller. Future adapters (Twilio webhook, queue worker, integration test harness) all need an obvious local entry point that accepts an inbound message, hands it to the modern pipeline, and returns the customer-facing responses. Subphase 3.29 adds that endpoint so the modern pipeline becomes reachable from `uvicorn backend.main:app` without bypassing the orchestrator or hand-rolling a wrapper.

## What Changes

- Add `backend/routers/incoming_messages.py` exposing `POST /comercios/{comercio_id}/clientes/{cliente_id}/incoming-messages` that returns the customer-facing responses for an inbound message against the active session of the given comercio / cliente pair.
- Add `backend/schemas/incoming_message.py` with `IncomingMessageRequest` (`message: str`) and `IncomingMessageResponse` (`responses: list[CustomerResponse]`) Pydantic models that act as the local HTTP contract.
- Resolve the active conversation through the existing `SessionService.get_active(comercio_id, cliente_id)` — reuse the same lookup that `GET /sessions/comercios/{comercio_id}/clientes/{cliente_id}/activa` already relies on; do not introduce a new repository query.
- Call `process_incoming_message_with_responses(db, session, message)` exactly once per request and return its `list[CustomerResponse]` wrapped in `IncomingMessageResponse`.
- Translate the existing exceptions: `SessionNotFound` → `HTTPException(404)`, `TypeError` / `ValueError` (raised by the inner validator when `message` is `None`, non-`str`, empty, or whitespace-only) → `HTTPException(400)` with the exception message preserved; all other exceptions propagate unchanged so the FastAPI default handler turns them into 500 without swallowing context.
- Wire the router in `backend/main.py` next to the existing `sessions` router; do not modify any other router, dependency, service, repository, intent module, recognizer, resolver, processor, handler, dispatcher, transactional wrapper, response builder, schema, model, migration, or LLM module.
- Add focused tests in `backend/tests/test_incoming_messages_endpoint.py` that drive the endpoint via FastAPI's `TestClient`, mock `SessionService.get_active` and `process_incoming_message_with_responses` at the router's import site, and assert status codes, payloads, and exception translation for: happy path (200), `agregar_producto` and unsupported-intent (200), `SessionNotFound` (404), `TypeError` from the pipeline (400), `ValueError` from the pipeline (400), and the `__all__` discipline on the router and schemas modules.
- Extend `openspec/specs/incoming-message-response-orchestrator/spec.md` with a new `ADDED Requirements` block documenting the local HTTP endpoint as the seam that exposes the modern pipeline to local callers.

## Capabilities

### New Capabilities

- `incoming-messages-local-http-endpoint`: Defines the local HTTP seam that exposes the modern intents pipeline. Covers the `POST /comercios/{comercio_id}/clientes/{cliente_id}/incoming-messages` route, the `IncomingMessageRequest` / `IncomingMessageResponse` Pydantic schemas, the single delegation to `process_incoming_message_with_responses`, the active-session lookup through `SessionService.get_active`, the deterministic translation of `SessionNotFound` / `TypeError` / `ValueError` to `HTTPException`, the response payload shape (`responses: list[CustomerResponse]`), the boundaries that keep this layer free of LLM calls, direct SQLAlchemy access, repository imports, mutation outside the modern pipeline, queue promotion, Twilio integration, retry / backoff, async wrappers, and logging, and the `__all__` discipline on the router and schemas modules.

### Modified Capabilities

- `incoming-message-response-orchestrator`: Adds documentation (not new behavior) for the local HTTP endpoint that delegates to `process_incoming_message_with_responses`. The orchestrator's behavior is unchanged; the addition is a single `ADDED Requirements` block recording that a local HTTP seam now exists and that callers must use it instead of hand-wiring the pipeline. No requirement-level behavior of the orchestrator itself changes.
