## Why

Subphase 3.30/3.30.1 gave us a working interactive HTTP CLI for exercising the modern intents pipeline end-to-end, but the loop is currently blind: after every typed line the user sees only the customer-facing response and has to trust the API. There is no way to verify "yes, that `agregar_producto` actually wrote a `Pizza de Muzzarella Grande x 2` into the draft `Pedido`" without dropping into psql or a second tool. Subphase 3.30.2 closes that loop by printing the current draft `Pedido` as a terminal table after every successful order modification, using only the running API. No new endpoint family is introduced; one new read-only production endpoint is added because the existing `GET /pedidos/{pedido_id}/productos` returns only `id_producto_presentacion` (a database id), which is not enough to render a human-readable table.

## What Changes

- **One new read-only HTTP endpoint: `GET /pedidos/{pedido_id}/detalle`.** Returns the pedido's scalar fields plus its line items enriched with the resolved product name and presentation description. Follows `Router → Service → Repository → SQLAlchemy`. Does not commit, rollback, flush, mutate, or load session/pedido relationships. Returns 404 when the pedido does not exist; returns 200 with an empty `lineas` array when the pedido exists with no line items.
- **New Pydantic response schema `PedidoDetalleResponse` in `backend/schemas/pedido.py`.** Reuses the existing `PedidoResponse` scalar fields and introduces a new minimal `PedidoDetalleLinea` schema carrying `cantidad`, `producto_nombre`, and `presentacion_descripcion` (no database ids, no `precio_unitario`, no `observaciones`, no `id_pedido_producto`). Reuses the existing `PedidoProductoRepository.list_by_pedido` whose eager-load chain already loads `ProductoPresentacion.producto`; the new repository method also joins `ProductoPresentacion.presentacion` so the description is available without a second query.
- **CLI extension in `backend/scripts/cli_chat_client.py`.** After every successful `POST /comercios/{comercio_id}/clientes/{cliente_id}/incoming-messages` call whose response list contains at least one `CustomerResponse` with `status == "executed"` and `intent in ORDER_MUTATING_INTENTS = {"agregar_producto", "quitar_producto"}`, the CLI issues exactly one `GET /pedidos/{pedido_id}/detalle` using the `pedido_id` it stored at bootstrap, prints the customer-facing responses first (unchanged behavior), then prints `Pedido actual:` followed by a plain-text table or `Pedido actual: vacío` for an empty order. If multiple executed mutation responses arrive in the same response list, the Pedido is retrieved only once. If the detail retrieval fails, the customer responses stay printed, a single-line warning is printed to `stdout` and the loop continues.
- **Pure helpers added to the CLI module**: `response_modified_order(responses) -> bool` and `format_order_table(lineas) -> str`. The order-mutating intent set is exposed as a module-level `ORDER_MUTATING_INTENTS = {"agregar_producto", "quitar_producto"}` constant. Table formatting uses only the Python standard library (`str` operations, dynamic width calculation from headers and values, `—` fallback for missing/empty presentation description, integer quantity rendering). No third-party table library is introduced.
- **No trigger for `pending_resolution`, `rejected`, `failed`, conversational intents, consultation intents, or any response that does not modify the Pedido.** No display of database ids in the table. No local recomputation of order state.
- **Strict import boundary preserved.** The CLI continues to use only `urllib.request` from the standard library; the new helpers do not import any `backend.*` module, no `fastapi`, no `sqlalchemy`, no `requests`/`httpx`/`aiohttp`/`websockets`. The existing `test_import_boundary` check is extended to assert the new helpers also stay within the boundary.
- **Tests** in `backend/tests/test_cli_chat_client.py` cover: executed `agregar_producto` triggers exactly one detail retrieval; executed `quitar_producto` triggers exactly one detail retrieval; `pending_resolution` / `rejected` / `failed` / conversational responses do not trigger any detail retrieval; multiple executed mutations in one response list trigger exactly one detail retrieval; the customer responses are printed before the table; the table contains product, presentation, and quantity columns; the table never exposes database ids; column widths adapt to long names; an empty order prints `Pedido actual: vacío`; a detail-retrieval failure prints a warning and the loop continues; the strict import boundary still holds. Tests mock `urllib.request.urlopen` and `builtins.input` and do not start a real server, DB, LLM, or subprocess.
- **No DB schema change. No Alembic migration. No new model. No new dependency.**

## Capabilities

### New Capabilities

_None._ The new endpoint slots into the existing `pedido-api` capability.

### Modified Capabilities

- `incoming-messages-interactive-cli`: After every successful `POST /comercios/{comercio_id}/clientes/{cliente_id}/incoming-messages` whose `responses` list contains at least one `CustomerResponse` with `status == "executed"` and `intent in {"agregar_producto", "quitar_producto"}`, the CLI SHALL issue exactly one `GET /pedidos/{pedido_id}/detalle` using the `pedido_id` stored at bootstrap, print the customer-facing responses first, then print `Pedido actual:` followed by a table (`Producto`, `Presentación`, `Cantidad`) or `Pedido actual: vacío`. Multiple executed mutation responses in the same list SHALL trigger exactly one detail retrieval. A detail-retrieval failure SHALL print a single-line warning and the loop SHALL continue. The CLI SHALL NOT trigger the detail retrieval for `pending_resolution`, `rejected`, `failed`, conversational, or consultation responses. The strict import boundary is preserved.
- `pedido-api`: Adds `GET /pedidos/{pedido_id}/detalle`, a read-only endpoint that returns the pedido's scalar fields and a `lineas` array. Each entry in `lineas` carries `cantidad` (int), `producto_nombre` (str), and `presentacion_descripcion` (str) — no database ids, no `precio_unitario`, no `observaciones`, no `id_pedido_producto`. The endpoint returns 404 when the pedido does not exist, 200 with an empty `lineas` array when the pedido exists with no line items, and never mutates the database. The response uses a new `PedidoDetalleResponse` schema in `backend/schemas/pedido.py`. The repository's `list_by_pedido` gains an additional eager-load of `ProductoPresentacion.presentacion` to make the presentation description available in a single query. The endpoint is read-only, performs no commit / rollback / flush / mutation, and follows the `Router → Service → Repository → SQLAlchemy` layering.
